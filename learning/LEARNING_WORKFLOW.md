# 项目学习闭环规范

## 1. 适用范围

本规范适用于 `learning/` 下所有现有和后续课程，不限定具体周次、技术领域或学习难度。

目标不是“看完课程”或“代码跑通”，而是形成可验证的能力：

```text
理解原理 → 完成实践 → 解释结果 → 诊断问题 → 迁移到新场景 → 延迟后仍能回忆
```

当前流程版本：`v1.2`。

---

## 2. 每日九阶段学习流程

每个阶段必须满足完成条件后才能进入下一阶段。必要时允许回退补课。

### 阶段 1：明确目标、边界和通过标准

课程开始时必须说明：

- 今天解决什么问题；
- 不学习什么，避免范围失控；
- 前置知识是什么；
- 最终产出是什么；
- 达到什么证据才算完成；
- 预计时间和认知负荷；
- 当前采用“学习模式”还是“任务完成模式”。

学习模式以形成理解和独立能力为目标，不能为了快速产出而由 Codex 包办关键判断。任务完成模式以交付结果为目标，只能由学习者明确切换，且不能把任务完成结果计入课程掌握证据。

完成条件：学习者能够用自己的话说明“今天学什么、为什么学、学到什么程度”。

### 阶段 2：前置知识诊断

- 一次只问一个明确问题；
- 只诊断本节课真正依赖的知识；
- 不把未讲授内容包装成测试；
- 对回答标记为：正确、不完整、错误、题目歧义。
- 如果连续两次回答“不知道”或明显缺少同一项前置知识，立即停止继续加难，进入针对性讲解。

诊断只用于选择教学起点，不用于给学习者贴标签。

完成条件：确认从哪里开始讲，以及哪些内容可以跳过。

### 阶段 3：建立理论模型

按以下顺序讲解核心知识：

1. 它是什么；
2. 为什么需要它；
3. 它怎样工作；
4. 它解决什么问题；
5. 它不能解决什么问题；
6. 它与已学概念的区别和联系；
7. 常见误区与工程边界。

优先使用 Java 类比，但类比后必须指出类比失效的地方。

讲解采用短循环，避免一次灌输过多内容：

```text
一个核心概念 → 一个具体示例 → 学习者复述或预测 → 精确反馈 → 再进入下一个概念
```

- 每轮原则上只引入一个主要新概念；
- 复杂内容先给整体地图，再逐个展开组件；
- 对可能变化的软件、模型、API 和最佳实践，优先查阅官方一手资料；
- 明确区分事实、主流共识、经验规则和当前推断；
- 同一点连续两轮仍然困惑时，停止继续追问，改用直接讲解、图示、反例或新的类比；
- 在主要阶段切换时，简要告知当前阶段、已完成证据和下一步，不在每轮输出冗余状态标签。

完成条件：学习者能用自己的语言复述因果链，而不只是背定义。

### 阶段 4：最小可运行实践

- 只保留验证核心原理所需的最少代码；
- 实践前先让学习者预测输入、关键过程和输出；
- 机械性代码可由 Codex 直接完成并验证；
- 学习者负责解释代码、运行结果和异常原因。

代码阅读默认采用“总—分—总”，不以逐行讲解作为完成标准：

1. **总览**：先说明文件职责、模块关系、入口、核心数据流和最终输出；
2. **核心拆解**：只阅读决定业务行为的核心函数、数据结构、状态分支、异常边界和关键第三方 API；
3. **按需补语法**：仅对阻碍理解的陌生语法进行局部讲解，不连续展开普通导包、打印、格式化和样板代码；
4. **回到整体**：最后由学习者复述输入如何经过核心代码变成输出，并指出失败路径。

只有在定位具体缺陷、审查安全关键代码、学习语言机制或学习者明确要求时，才进行逐行阅读。代码阅读的目标是理解架构、关键数据流和设计取舍，而不是解释文件中的每一个字符。

完成条件：程序通过验证，且学习者能解释关键数据流。

### 阶段 5：工程化扩展

从最小示例扩展到真实开发需要关注的内容：

- 模块边界与复用；
- 配置与密钥管理；
- 异常、空值和边界条件；
- 性能、资源和成本；
- 日志、调试和可观测性；
- 安全、测试和可维护性；
- 适用场景与不适用场景。

完成条件：学习者能指出示例代码距离生产代码还缺什么。

### 阶段 6：三层测试

测试不能只重复实践代码，必须包含三个层次：

1. **概念理解**：解释原理、因果关系和概念边界；
2. **代码诊断**：阅读新代码，预测结果、发现错误并说明根因；
3. **场景迁移**：面对未练习过的业务场景，选择方案并说明取舍。

每次只提出一个问题。选择题只适合快速诊断，不能作为唯一掌握证据。

每一层至少包含一次没有照抄原练习的独立回答。某层未通过时，回到对应教学阶段补讲，并使用不同题目重新测试，不能用原题答案代替掌握证据。

完成条件：三个层次均达到掌握门槛；任何一层未通过，都不能把当天课程标记为“已掌握”。

### 阶段 7：独立决策任务

给出一个信息不完全但边界明确的新场景，由学习者负责：

- 判断是否应使用本节技术；
- 设计核心方案；
- 识别风险和失败条件；
- 定义验收指标；
- 解释取舍。

Codex 可以完成重复编码，但不能替代学习者做核心判断。

完成条件：学习者能在没有照抄示例的情况下作出有依据的决策。

### 阶段 8：笔记和证据化评估

每天的 `notes.md` 至少记录：

- 学习目标与边界；
- 核心知识模型；
- 学习者自己的费曼解释；
- 实践代码及验证结果；
- 错误、误区和修正过程；
- 持续误区清单：错误想法、形成原因、正确模型和识别线索；
- 三层测试结果；
- 可供后续主动回忆的题库，标记概念、诊断或迁移类型；
- 独立决策任务结果；
- 尚未掌握的内容；
- 掌握程度及证据；
- 当前学习状态和下一次继续位置；
- Day +1、Day +7、Day +30 的复习日期。

### 阶段 9：延迟复习

- **Day +1**：先不看笔记复述核心模型，再完成一道概念或代码诊断题；
- **Day +7**：先从题库随机抽题，再完成一个变式场景，检查是否能够迁移；
- **Day +30**：完成综合任务，并用费曼方式向初学者讲解，判断知识是否进入长期记忆。

复习必须先检索记忆、后查看笔记。直接重读笔记不能计为完成复习。

复习结果写回原课程笔记，不另建无法追踪的零散记录。

## 3. 自适应教学控制

### 3.1 教学决策依据

每一步根据四类信号选择下一动作：

| 信号 | 下一动作 |
|---|---|
| 回答正确且能解释原因 | 提升一个难度或进入下一阶段 |
| 结论正确但原因不完整 | 只补当前最关键缺口，再让学习者复述 |
| 回答错误但暴露了明确心智模型 | 用反例修正该模型，不直接堆更多定义 |
| 连续困惑、疲劳或挫败 | 停止苏格拉底追问，直接讲解并降低单步难度 |

### 3.2 防止“虚假流畅”

以下现象不能当作已经掌握：

- 看着示例觉得懂；
- 跟着步骤成功运行；
- 记住选择题答案；
- 在提示下复述定义；
- Codex 完成了代码，学习者只看到了结果。

必须通过闭卷复述、预测、错误诊断或新场景迁移中的至少一种行为证明理解。

### 3.3 学习状态持久化

当天笔记必须保存：当前阶段、已通过门槛、未通过门槛、持续误区和下一步。新会话先读取这些状态再继续，不能只依赖聊天上下文。

## 4. 提问协议

每道问题必须包含一个明确的回答对象。例如：

```text
对象：PDF 页面的 metadata
问题：为什么每个切分后的 Chunk 都需要复制这份 metadata？
只回答：如果不复制，会对检索结果追溯造成什么影响？
```

禁止：

- 在同一道题中混入多个未编号的问题；
- 使用“你觉得呢”“说说看”等没有边界的问法；
- 问完第一个问题后按第二个问题的标准评价答案；
- 在未讲授必要知识时要求学习者凭空回答；
- 因表达方式不同而把正确理解判断为错误。

反馈格式：

```text
判断：正确 / 不完整 / 错误 / 题目歧义
依据：对应用户回答中的具体内容
缺口：只指出当前最关键的一处
下一步：补充讲解或一个后续问题
```

## 5. 掌握程度标准

星级必须来自证据，不能凭课堂顺利程度或代码是否运行来判断。

| 等级 | 可观察证据 |
|---|---|
| ★☆☆☆☆ | 听过术语，但无法准确解释 |
| ★★☆☆☆ | 能说出定义和用途，需要提示 |
| ★★★☆☆ | 能运行并读懂示例，能解释主要数据流 |
| ★★★★☆ | 能诊断错误，并把知识迁移到新场景 |
| ★★★★★ | 能独立设计、权衡、验证，并清楚地教给别人 |

当天通常只能证明前三至四星。五星需要延迟复习和新场景证据。

## 6. 每日复盘模板

课程结束后，师生共同回答：

1. 今天哪些目标已经有证据证明完成？
2. 哪些地方只是“听懂”，还没有形成能力？
3. 哪个问题、示例或实践最有效？为什么？
4. 哪个问题存在歧义、过浅或跨度过大？
5. 学、练、测、评、复五个环节哪个最弱？
6. 下一节课必须执行的具体改进是什么？
7. 今天是否出现了连续追问、一次灌输过多或 Codex 包办关键思考？
8. 哪个持续误区需要进入后续题库和延迟复习？

复盘必须产生可执行变更，例如“场景迁移题增加失败条件”，而不是只写“加强练习”。

---

## 7. 流程迭代记录

发现流程问题时，按以下顺序处理：

1. 在当天 `notes.md` 记录原始问题和证据；
2. 提出具体改法；
3. 在下一课程中验证；
4. 验证有效后更新本规范的版本和规则；
5. 在 Git 中保留变更历史。

不要因为单次体验立即加入大量规则，也不要只复盘而不修改后续行为。

---

## 8. 抽象为通用 Learning Skill 的条件

暂不直接创建 Skill。先把本规范作为项目内实验流程，满足以下条件后再抽象：

- 至少完成 5 个完整课程闭环；
- 覆盖至少 3 类知识，例如理论概念、编程实践、系统设计；
- 至少执行过一次 Day +7 延迟复习；
- 连续 3 次课程没有出现流程级重大调整；
- 已积累真实的优质提问、失败提问、评估证据和复盘样本。

届时 Skill 应保持精简：

```text
learning-coach/
├── SKILL.md
├── agents/openai.yaml
└── references/
    ├── assessment-rubric.md
    ├── question-patterns.md
    └── note-template.md
```

创建后必须执行格式校验，并用不同领域的新任务进行前向测试，验证它不是只适用于当前 AI 课程。

## 9. 设计参考与版本记录

本流程选择性吸收以下成熟机制，但不直接复制任何单一产品：

- ChatGPT Study Mode：分层讲解、主动参与、元认知和认知负荷管理；
- learn-codebase：先预测后揭示、主动回忆、间隔复习和持久学习日志；
- DeepTutor：题库、掌握路径、可审计记忆和学习状态持久化；
- 苏格拉底教学 Skill：逐级诊断、一次一个问题和困惑停止阈值。

### v1.2

- 代码阅读改为“总—分—总”：先整体架构，再核心代码，最后回到完整数据流；
- 默认跳过普通导包、打印、格式化和样板代码的逐行解释；
- 只有调试、安全审查、语言机制学习或学习者明确要求时才逐行阅读；
- 将“能解释关键数据流和失败路径”作为代码理解证据，而不是“读完所有行”。

- 区分学习模式与任务完成模式；
- 增加认知负荷控制和短讲解循环；
- 增加连续困惑时切换直接讲解的规则；
- 为三层测试增加硬性掌握门槛；
- 增加持续误区、题库和学习状态记录；
- 强化先主动回忆、后查看笔记的延迟复习方式。
