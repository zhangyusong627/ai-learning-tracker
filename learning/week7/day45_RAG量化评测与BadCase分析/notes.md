## 一、业务目标

原有 RAG 冒烟测试只能证明：

- 文档可以解析和切块；
- 向量可以写入数据库；
- 查询可以返回候选证据；
- 机构元数据（metadata）过滤生效；
- 至少一次查询能够产生可采纳证据。

它不能证明检索质量稳定。今天的目标是建立人工标注的黄金查询集，用量化指标回答：

1. 正确证据能否进入前 K 条；
2. 正确证据排得是否足够靠前；
3. 返回结果中有多少噪声；
4. 阈值过滤后还保留了多少正确证据；
5. 知识库没有答案时能否正确拒答；
6. 机构范围过滤是否发生串库。

## 二、先学清楚的指标

### 1. 前 K 条命中率（Hit@K）

对每个查询检查前 K 条，只要至少有一条正确证据就记为 1，否则记为 0，再对全部查询取平均。

例如 10 个独立查询中有 8 个查询在前 5 条找到正确证据：

```text
Hit@5 = 8 ÷ 10 = 80%
```

这里的 5 是“每个查询检查前几条”，8 是“10 个查询中成功了几个”，不是 5 条结果里装了 8 条证据。

### 2. 前 K 条查准率（Precision@K）

```text
前K条查准率 = 前K条结果中的正确证据数 ÷ K
```

前 5 条中有 1、3、5 条正确证据时，Precision@5 分别为 20%、60%、100%。

### 3. 前 K 条召回率（Recall@K）

```text
前K条召回率 = 前K条找回的正确证据数 ÷ 应找到的正确证据总数
```

应该找到 4 条、实际找回 2 条时，Recall@5 为 50%。

### 4. 平均倒数排名（MRR）

只看第一条正确证据的排名：

```text
排第1：1 ÷ 1 = 1
排第2：1 ÷ 2 = 0.5
排第5：1 ÷ 5 = 0.2
没找到：0
```

全部查询的倒数排名得分取平均，就是平均倒数排名。

### 5. 无答案拒答率

```text
无答案拒答率 = 正确拒绝的无答案查询数 ÷ 无答案查询总数
```

它衡量系统在没有证据时是否会把语义相似但不支持问题的内容当成答案。

### 6. 候选召回与可采纳证据召回不是一个口径

链路分为：

```text
向量检索前K条候选 → 距离阈值过滤 → 可采纳证据
```

- 前 K 条召回率：计算阈值过滤前的候选结果；
- 可采纳证据召回率：计算阈值过滤后真正进入 LLM 上下文的证据。

降低最大距离阈值不会改变候选排序，所以理论上不会改变前 K 条召回率；它可能降低可采纳证据召回率，同时提高无答案拒答率。

## 三、黄金评测集设计

第一版建立 15 条查询：

| 类型 | 数量 | 目的 |
|---|---:|---|
| 字段映射与文件传输 | 6 | 验证精确字段、单位转换和机构差异 |
| 跨接口阶段依赖 | 3 | 验证 `applyId` 等阶段结果来源 |
| 机构范围隔离 | 3 | 验证同一问题在三家机构范围内不串库 |
| 无答案拒答 | 3 | 验证 QPS、活体阈值、生产表名等缺失事实不会被编造 |

黄金证据不绑定某次切块产生的 `chunk_id`，而是标注：

```json
{
  "document": "恒誉消金产品接入需求说明书.md",
  "locator_contains": "6. 字段映射要求",
  "required_terms": ["request.amount", "loanAmount", "yuan_to_cent"]
}
```

原因：如果将标准答案写死为 chunk ID，调整切块策略后评测标准也会失效，无法公平比较新旧切块方案。

## 四、第一次基线为什么不可信

第一次运行得到：

- Hit@5：66.67%；
- Recall@5：66.67%；
- 无答案拒答率：0%。

随后检查索引发现：Word/Excel API 文档的 chunk 被统一标成 `institution=unknown`。机构过滤后，这些文档根本没有进入候选集，主要只有 Markdown 需求文档参与竞争，因此分数被不完整的小候选集虚高。

根因代码位于统一解析器：

```python
institution = "unknown"
```

DOCX、PDF、XLSX 三种解析路径都固定使用该值，索引调用方也没有显式传入机构编码。

## 五、元数据修复决策

没有根据文件名猜测机构，因为文件名不是可靠的业务元数据来源。最终方案是：

1. `parse_document()` 接受可信调用方显式传入的机构编码；
2. Chroma 索引入口要求 `--input` 与 `--input-institution` 一一对应；
3. 机构编码同时写入 ParseResult 和文档块元数据；
4. 只传部分机构编码时直接报错，防止生成“半正确”索引；
5. 增加 DOCX/XLSX 元数据回归测试。

修复结果：

| 机构 | chunk 数 |
|---|---:|
| 恒誉消金 | 278 |
| 云腾数科 | 269 |
| 衡丰银行 | 293 |
| 合计 | 840 |
| `institution=unknown` | 0 |

## 六、修复后的真实基线

完整语料进入候选集后：

| 指标 | 结果 |
|---|---:|
| Hit@5 | 50.00% |
| Precision@5 | 10.00% |
| Recall@5 | 50.00% |
| MRR | 0.3542 |
| 可采纳证据精度 | 10.00% |
| 可采纳证据召回率 | 50.00% |
| 无答案拒答率 | 0.00% |
| 机构范围过滤通过率 | 100.00% |

指标下降不是修复导致系统退化，而是完整 API 文档真正参与排序后，候选从少量 Markdown chunk 增加到每家约 270～293 个 chunk。新结果才是真实基线。

Precision@5 为 10% 还与评测集结构有关：12 个可回答问题通常各有 1 条黄金证据，6 个成功用例各贡献 20%，6 个失败用例贡献 0%，平均后为 10%。它不能脱离黄金证据数量单独解释。

## 七、距离阈值探索

对同一黄金集扫描多个最大距离阈值：

| 距离阈值 | Hit@5 | Recall@5 | 可采纳证据精度 | 可采纳证据召回率 | 无答案拒答率 |
|---:|---:|---:|---:|---:|---:|
| 0.30 | 50.00% | 50.00% | 6.53% | 25.00% | 100.00% |
| 0.35 | 50.00% | 50.00% | 11.94% | 41.67% | 33.33% |
| 0.40 | 50.00% | 50.00% | 10.00% | 50.00% | 33.33% |
| 0.45 | 50.00% | 50.00% | 10.00% | 50.00% | 33.33% |
| 0.50 | 50.00% | 50.00% | 10.00% | 50.00% | 0.00% |
| 0.60 | 50.00% | 50.00% | 10.00% | 50.00% | 0.00% |
| 0.85 | 50.00% | 50.00% | 10.00% | 50.00% | 0.00% |

结论：

- `0.30` 可以拒绝全部无答案查询，但误杀大量正确证据；
- `0.40` 保留 50% 的可采纳证据召回率，但只能拒绝 1/3 无答案查询；
- `0.50` 以上三个无答案查询全部被放行；
- 当前不存在一个能够同时保证召回与拒答的全局距离阈值。

因此不能凭感觉把 `0.85` 改成 `0.40`，也不能只靠阈值解决检索质量问题。

## 八、Bad Case（失败用例）根因

### 1. 纯向量检索不擅长精确字段

失败查询集中包含：

- `applyId`；
- `loanAmt` / `loanAmount`；
- `stage_result.credit.apply_id`；
- 元转分规则 `yuan_to_cent`。

向量模型擅长语义相似，但对驼峰命名字段（camelCase）、阶段路径、接口名和编码不够敏感。

### 2. 通用标题和简介抢占排名

“恒誉消金生产接口允许的最大 QPS”查询中，前三条分别是：

- 机构合作人员说明；
- 文档标题；
- 对外接口简介。

这些内容与“恒誉消金接口”主题相似，但完全没有 QPS 数值。

这证明：

```text
向量相似度 ≠ 证据支持关系
```

### 3. 表格切块上下文不足且存在重复

API 文档同时生成：

- 单行表格 chunk；
- 完整表格 chunk；
- 独立标题和段落 chunk。

单独一行可能只有 `loanAmt | integer | 单位分`，缺少接口名、表头和平台字段；完整表格与单行又会互相竞争 Top-K。

### 4. 过滤维度仍然过粗

机构过滤已经 100% 正确，但每家仍有约 270～293 个 chunk。当前没有稳定利用操作、接口和内容类型进一步缩小候选范围。

## 九、下一步修复顺序

1. 让评测脚本自动保存失败用例的前 20 条候选、距离、定位和黄金证据实际排名；
2. 优化表格切块为“章节 + 表头 + 当前数据行”，控制重复 chunk；
3. 增加关键词召回，重点处理字段名、接口名、编码和阶段路径；
4. 使用倒数排名融合（Reciprocal Rank Fusion）合并向量与关键词排名；
5. 增加二次排序或证据支持校验；
6. 最后再用同一黄金集校准距离阈值；
7. 扩充黄金集并拆分校准集与保留测试集，避免针对 15 条查询过拟合。

禁止通过以下方式制造 PASS：

- 修改黄金标注去迎合当前结果；
- 只挑选成功查询展示；
- 盲目把 Top-K 从 5 扩大到 20；
- 单独调整阈值而不比较召回和拒答；
- 把单条冒烟测试的 PASS 描述成检索质量合格。

## 十五、修复方案实施结果

本节记录上述“下一步修复顺序”的真实实施结果。它不是计划描述，数据来自改造后的同一套 15 条黄金集。

### 1. 失败诊断报告

评测指标仍严格使用前 5 条，另外保留前 20 条只用于排查。报告现在会保存候选距离、文档、定位、内容摘要、正确证据实际排名，并自动区分：

- 正确证据排在前 5 条之后；
- 正确证据未进入前 20 条；
- 正确证据被阈值误杀；
- 错误证据被采纳；
- 无答案问题被伪相关证据放行；
- 机构元数据越界。

诊断结果证明：部分阶段依赖证据排在第 11 或第 17，另一些字段映射证据连前 20 条都没有进入。因此不能通过把正式 Top-K 改成 20 来掩盖排序问题。

### 2. 表格上下文切块

旧索引同时包含缺少上下文的单行表格、完整表格和独立表头，存在重复竞争。第一次尝试对所有表格都只保留数据行，结果 Hit@5 从 66.67% 降到 41.67%：身份证正反面、人脸等列表问题必须同时看到多行，单行切块破坏了整体语义。

最终采用多粒度策略：DOCX/XLSX 数据行补齐章节和表头；Markdown 小表同时保留整表与数据行，大表保留数据行。数据行统一形成：

```text
章节: 4.7 用信申请接口
表头: 参数名 | 数据类型 | 是否必填 | 说明
当前行: loanAmount | integer | Y | 用信金额，单位分
```

解析层仍保留原始完整表格供文档质量检查。多粒度重建后共有 855 个文档块；数量不是优化目标，能否同时支持列表问题和精确字段问题才是判断标准。

### 3. 关键词召回与倒数排名融合

新增轻量 BM25 关键词通道和金融接入查询扩展，重点识别：

- 驼峰字段，例如 `loanAmount`、`applyId`；
- 下划线路径和阶段结果；
- 接口名、编码和英文缩写；
- 中文双字关键词；
- “用信申请金额”等中文业务词到 `loanApply`、`amount/amt`、`yuan_to_cent` 等接口词的映射。

另外增加查询意图排序，使用“字段映射章节、平台字段、机构字段、转换规则、`stage_result`、禁止重新触发”等通用结构信号。向量、BM25 和查询意图三路排名通过倒数排名融合（RRF）合并。RRF 比较的是名次，不直接比较量纲不同的原始分数。

### 4. 事实锚点证据支持校验

距离较近只能说明主题相似，不能证明内容支持问题。新增确定性事实锚点闸门：问题中出现 QPS、阈值、表名或 `applyId` 等明确事实锚点时，候选原文必须包含对应锚点，否则不能进入可采纳证据。

该规则使三个无答案问题都被正确拒绝，但它只是适合明确技术事实的第一层校验，不能替代通用语义重排模型。

### 5. 新旧指标对比

| 指标 | 纯向量旧基线 | 混合检索新基线 | 变化 |
|---|---:|---:|---:|
| Hit@5 | 50.00% | 100.00% | +50 个百分点 |
| Precision@5 | 10.00% | 25.00% | +15 个百分点 |
| Recall@5 | 50.00% | 100.00% | +50 个百分点 |
| MRR | 0.3542 | 0.7389 | +0.3847 |
| 可采纳证据精度 | 10.00% | 33.33% | +23.33 个百分点 |
| 可采纳证据召回率 | 50.00% | 91.67% | +41.67 个百分点 |
| 无答案拒答率 | 0.00% | 100.00% | +100 个百分点 |

### 6. 最终阈值选择

改造后重新扫描 `0.30` 至 `0.85`。候选排序指标不随阈值变化；`0.50` 是可采纳证据召回率达到 90% 目标的最严格阈值，并且在达标档位中精度最高，因此默认阈值从旧值调整为 `0.50`。

无答案拒答率在各阈值下都为 100%，说明改进来自事实支持校验，而不是单纯把阈值调严。

| 距离阈值 | 可采纳证据精度 | 可采纳证据召回率 | 无答案拒答率 |
|---:|---:|---:|---:|
| 0.30 | 5.00% | 25.00% | 100.00% |
| 0.35 | 19.58% | 50.00% | 100.00% |
| 0.40 | 21.25% | 58.33% | 100.00% |
| 0.45 | 28.33% | 66.67% | 100.00% |
| 0.50 | 33.33% | 91.67% | 100.00% |
| 0.60 | 29.03% | 100.00% | 100.00% |
| 0.85 | 26.94% | 100.00% | 100.00% |

`0.60` 虽然把召回提高到 100%，但精度低于 `0.50`。因此选择满足 90% 目标且噪声更少的 `0.50`，而不是追求单项指标最高。

### 7. 当前真实结论

当前 15 条黄金集已达到 Hit@5 100%、Recall@5 100%、可采纳证据召回率 91.67%、无答案拒答率 100%，并加入了最低 90% 的自动化质量闸门，不达标时脚本返回非零状态。

但这 15 条用例参与了调试，只能说明当前基线达标，不能描述为生产准确率或泛化能力。Precision@5 仍为 25%，可采纳证据精度为 33.33%，下一步必须建立未参与调参的独立保留测试集，并继续减少非黄金候选。

2026-08-06 收尾时进一步删除了未对齐的第二套向量后端，只维护 Chroma 混合检索。原因是双链路会扩大维护面并产生能力漂移，而作品集当前需要证明的是解析、排序、证据边界和生成追溯，不是基础设施数量。

衡丰 API 文档从重复的 DOCX 形态调整为带中文文本层的 PDF 后，重新解析并重建 Chroma 索引，共得到 1282 个文档块。chunk 数增加主要来自 PDF 按页内文本块切分，不代表质量自然提高；回归结果为 MRR 0.7389，其他核心闸门保持通过。

当前 Chroma 实现会在机构过滤后的语料范围内计算 BM25 和精确余弦排名，适合当前本地作品集演示；大规模生产语料应使用受控候选池与可扩展的全文检索方案，不能照搬全量内存排序。

## 十六、新 PDF 全链路复核中的问题与修复

2026-08-06 对衡丰新 PDF 重新执行“解析 → 切块 → Chroma 入库与检索 → AI 识别 → 人工确认 → Java 生成 → 测试 → 追溯”时，发现了四类不能只靠“脚本 PASS”判断的问题。

### 1. 文档识别输入与代码生成上下文不能混用

旧流程把 Top-K 检索结果同时用于结构化识别和代码生成。结构化识别脚本还会截断过长输入，导致版本号和部分字段没有进入模型。修复后拆成两份输入：

- `extraction_input.md`：完整规范化需求文档和 API 文档，专供 AI 识别全部接口与字段；
- `llm_input_context.md`：检索证据、公共映射和范式代码，专供 Java 生成。

结论：需要“完整理解”的环节不能只吃 Top-K；需要“聚焦生成”的环节才适合检索裁剪。

### 2. API 文档入库不等于生成代码使用了 API 文档

第一次生成后的追溯记录显示，11 个 Java 方法引用的证据全部来自需求说明书，新 PDF 虽然已解析、切块和入库，却没有真正进入最终代码依据。

修复方式：

- 为 4.1 至 4.11 每个接口增加定向检索问题；
- 在证据目录中明确标记当前 API 文档文件名；
- 生成阶段要求每个方法至少引用一条该 API 文档证据；
- 最终追溯校验再次检查文档来源，不能只检查证据编号是否存在。

复核结果：81 条可用证据中 52 条来自新 PDF；11 个 Java 方法都至少直接引用一条新 PDF 证据。

### 3. 编译通过仍可能违反业务约定

第一次重新生成的代码能够编译，但 `applyLoan` 把公共路由参数 `isFenceFlag` 重复写进业务报文，并把缺省值当作错误，导致契约测试失败。

根因是“字段映射”只描述了字段对应关系，没有区分它由业务 body 承载，还是由客户端传输层参数承载。修复后把规则固化为：

- `isFenceFlag` 统一由 `fenceFlag(vars)` 读取；
- 缺省值为 `false`，表示直连；
- 作为 `client.call` 的路由参数传递；
- 禁止再执行 `body.put("isFenceFlag", ...)`；
- 增加确定性单元测试，不能只依赖提示词提醒模型。

### 4. 测试报告也必须验证统计逻辑

Golden 评估原来会把 Maven 同一组测试的两次摘要相加，9 条被报告为 18 条。修复后只读取 Maven 最终汇总，并增加重复摘要回归测试。

本次最终结果：

- 真实 DeepSeek 重新生成 11 个方法；
- Maven 编译通过；
- 9 条契约/标准答案测试通过，失败 0，错误 0；
- 11 个方法数量检查通过；
- Golden 关键代码特征检查通过；
- 11 个方法的 PDF 证据追溯检查通过。

面试可讲的核心不是“最后全绿”，而是：我发现“文档已经入库”不代表“代码真的依据该文档生成”，于是把来源约束做成生成前后两道确定性闸门，并用编译、业务测试和方法级追溯分别验证语法、行为和证据来源。
