# 🟦 第一部分 · 通用概念层（与项目解耦）

## 一、架构与数据流

#### 1-1 🟢 一个 RAG 系统分为哪两个阶段？各自什么时机执行、运行频率有何不同？

<details>
<summary>参考答案</summary>

**离线索引阶段**：文档更新时执行一次（解析 → 切块 → 向量化 → 持久化到向量数据库）。建一次索引，可被无数次检索复用。

**在线检索 + 抽取阶段**：每次查询都执行（embedding 查询 → 向量检索 → 证据打包 → LLM 抽取 → 审批）。

区分两者是 RAG 的核心分界——把索引和检索混成一个管道会掩盖"建一次索引可复用"这个关键生产特性。

</details>

#### 1-2 🟢 在 RAG 里，检索结果如何成为 LLM 的输入？为什么 LLM 不直接读原始文档？

<details>
<summary>参考答案</summary>

检索的产物被打包成"编号证据上下文"，直接作为 LLM 的输入。LLM **看不到原始文档**，只看到这份带文档名 + 定位 + 原文的证据上下文。

这正是 RAG 中"增强（Augmented）"的含义——用检索到的真实证据替代 LLM 凭训练数据凭空生成。本项目里这份衔接文件叫 `llm_input_context.md`，但"检索产物 = LLM 输入"这个结构是通用的，换任何项目都成立。

</details>

#### 1-3 🟡 为什么"检索产物 = LLM 输入"是 RAG 的核心？跳过检索直接把全部文档喂给 LLM 会怎样？

<details>
<summary>参考答案</summary>

问题有三：
1. **上下文超限**：全部文档可能远超 LLM 上下文窗口
2. **噪音干扰**：多份文档几百个 chunk，大部分与当前任务无关，LLM 会被误导
3. **无法溯源**：不经过证据编号，LLM 输出无法引用"哪份文档哪一段"，人工审批无从核对

RAG 的价值就是"用检索到的真实证据增强生成"，避免 LLM 凭训练数据瞎编。

</details>

#### 1-4 🟡 向量检索返回的 Top-K 结果，和最终喂给 LLM 的证据，为什么是两回事？中间为什么要做距离阈值过滤？

<details>
<summary>参考答案</summary>

Top-K 只是"向量空间里最相似的 K 个"，**不代表都足够相关**——库里没有更相关内容时，不相关的内容也会被塞进 Top-K。

距离阈值过滤（本项目叫 `accepted_evidence`，区别于原始 `retrieved_candidates`）保留的是"距离 ≤ 阈值"的可信证据。给 LLM 的必须是过滤后的证据：直接把全部候选喂给 LLM，等于把不相关内容当证据，LLM 会基于错误证据编造答案。

保留"候选"和"证据"两个概念，本质是在区分"检索到了"和"可信"。

</details>

#### 1-5 🟡 做"结构化接口抽取"时，为什么不能只给接口文档、也不能只给需求文档？缺其一抽取结果有什么缺陷？

<details>
<summary>参考答案</summary>

- **需求文档**（行为规格）：定义接入逻辑——调用顺序、字段映射方向、跨接口依赖、配置项清单
- **接口文档**（技术规格）：定义接口细节——URL、请求/响应字段名、数据类型、认证方式

**只有接口文档** → LLM 知道接口长什么样，但不知道调用顺序和依赖关系，流程靠猜
**只有需求文档** → LLM 知道要做什么，但不知道字段名和 URL，字段映射靠编——联调全报 400

两者缺一不可：需求定义"怎么接入"，接口定义"接口长什么样"。这是通用规律，本项目用"产品需求文档 + 机构 API 文档"这对组合落地。

</details>

#### 1-6 🟡 做带元数据的检索时，元数据过滤为什么必须在 Top-K 排序之前执行？

<details>
<summary>参考答案</summary>

反例：先全库 Top-K 返回 12 条，其中 10 条是其他主体的——应用层再过滤只剩 2 条，丢了本该召回的；更危险的是如果忘了过滤，会把不相关主体的内容当证据喂给 LLM。

先过滤（如 `WHERE institution='X'`）再 Top-K，搜索空间先限定——"没搜到"是明确的空结果（触发 fail-on-empty），而不是"搜到了但都是错的"。这是多租户 / 多主体知识库共存的通用铁律。

</details>

## 二、文档解析

#### 2-1 🟢 解析一个文档时，应该有哪些"状态"来刻画解析结果？各对应什么场景？

<details>
<summary>参考答案</summary>

| 状态 | 场景 |
|---|---|
| 成功 | 完整解析成功 |
| 部分成功 | 部分成功——比如 PDF 5/10 页有文本，另外 5 页是扫描件 |
| 失败 | 完全失败——文件损坏、依赖库未装 |
| 需 OCR | 无文本层需要 OCR——扫描版 PDF |

细粒度状态让错误处理有据可依，而不是一律"成功/失败"二元。

</details>

#### 2-2 🟡 "部分成功"状态的设计意义？为什么不直接报失败？

<details>
<summary>参考答案</summary>

"部分成功"让调用方**知情决策**：文档解析不完美但可能还能用。直接报失败太粗暴（丢 85% 信息），假装成功又掩盖问题。

配合一个"要求完整解析"的开关：默认严格模式下，部分成功被当作不可入库处理（除非显式允许），保证"你不明确的失败不会悄悄进知识库"。这是解析容错的通用做法。

</details>

#### 2-3 🟡 为什么文档切块后要保留"定位信息"（页码/章节/段落/表格索引）？每条证据为什么要带定位？

<details>
<summary>参考答案</summary>

定位信息让每个文档块都能**追溯到原始位置**。

因为 LLM 抽取结果的每条结论都要带证据（文档 + 定位 + 原文），审批人需要对照原文核对——没有定位信息，"这条结论对不对"就无从核实。定位溯源是整个"人工在环"审批链的可信基础，也是 RAG 可解释性的通用要求。

</details>

#### 2-5 🟡 扫描版 PDF（纯图片）应该报哪个状态？为什么不直接报失败？

<details>
<summary>参考答案</summary>

报"需 OCR"，不是失败。

因为文件本身没坏，只是**没有文本图层**——它是"格式正确但内容无法直接提取"而不是"解析失败"。报"需 OCR"告诉下游"这条有救，但需要先过 OCR 才能入库"，而失败表示"放弃这条文档"。四态模型（成功/部分成功/失败/需 OCR）让错误处理有了细粒度。

</details>

## 三、文本切块

#### 3-1 🟢 chunk（文本块）是什么？为什么不能把整份文档当一个索引单元？

<details>
<summary>参考答案</summary>

chunk 是向量检索的**最小索引单元**——一份文档切成若干小块，每块单独 embedding、单独入库。

不能整篇入库：① 单篇可能几百 KB，embedding 一次、检索命中一整篇，精度极低；② LLM 上下文有限，喂一整篇浪费 token 还引入噪音；③ 检索需要"命中到具体段落"，而不是"命中整篇文档"。

</details>

#### 3-2 🟡 chunk 大小和"重叠（overlap）"各是什么？overlap 为 0 会怎样？

<details>
<summary>参考答案</summary>

- chunk 大小 = 每块最多多少字符，超过继续切下一块
- 重叠 = 相邻两块前后重叠若干字符

overlap=0 的后果：一句话可能被切成两块——块 A 结尾"applyId 该参数由授信查"，块 B 开头"询接口的返回中获取"。检索命中 A 看不到"从哪里获取"，命中 B 不知道主语是 applyId，信息在 chunk 边界断裂。重叠让关键信息不因切块而丢失。经验值：中文金融文档 500-1000 字，重叠 10%-15%。

</details>

#### 3-4 🟡 固定长度切块 vs 语义切块 / 递归切块 / 结构感知切块，各有什么权衡？

<details>
<summary>参考答案</summary>

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 固定长度 | 硬切 N 字 | 简单、确定性 | 可能在句子中间切断 |
| 语义切块 | 相邻句子 embedding 相似度低处切 | 语义保真最佳（按相似度聚拢，块内最连贯） | 额外计算开销 |
| 递归切块 | 对超 chunk_size 的块，按段落→句子→字符逐级换分隔符再切（够小的块直接保留） | 主流框架默认，平衡 | 对表格不友好 |
| 结构感知 | 按标题层级切 | 结构保真最佳（保留标题/表格/列表单元，不被切碎） | 需要文档有清晰结构 |

生产级优先结构感知或语义切块；固定长度是"最小可行选择"。

</details>

#### 3-5 🔴 chunk 大小对检索效果的影响规律？

<details>
<summary>参考答案</summary>

- **太小**（200 字）：命中聚焦但上下文断裂（一句话被切成两块）
- **太大**（2000 字）：上下文完整但噪音多（一块里混着多个话题），浪费 token
- **经验值**：中文金融文档 500-1000 字；代码类更短（300-500）；叙事类可长（1000-1500）

</details>

## 四、向量化

#### 4-1 🟢 embedding（文本向量化）是什么？为什么"语义相近的文本向量距离也近"？

<details>
<summary>参考答案</summary>

embedding = 把一段文本转成固定维度的浮点数数组。模型在训练时学会了把"语义相近的文本映射到空间里相近的位置"，所以"借款申请"和"贷款提交"的向量会靠得近，而和"北京天气"离得远。检索的本质就是找"向量距离最近的文本"。

</details>

#### 4-2 🟡 索引阶段和检索阶段的 embedding 配置为什么必须完全一致？不一致会怎样？

<details>
<summary>参考答案</summary>

embedding 配置四项（provider / model / dimension / normalize）。如果索引用模型 A（512 维），检索换了模型 B，向量不在同一个空间，距离比较毫无意义——相当于拿"公斤"和"磅"直接比大小。

原则：**配置不匹配宁可报错，不能默默返回垃圾结果**。本项目在 Chroma 索引与检索链路中做了强制校验（实现见 🟧 6-5）。

</details>

#### 4-3 🟡 向量 L2 归一化的作用？归一化后余弦相似度和内积的关系？

<details>
<summary>参考答案</summary>

L2 归一化把向量缩放到单位长度（模长为 1）。归一化后向量落在同一超球面上，**余弦相似度 = 内积**。

如果不归一化，向量模长各不相同，内积和余弦不再等价——可能出现"内积大但余弦小"的矛盾。设置余弦距离检索的前提就是向量已归一化。

</details>

#### 4-4 🔴 换 embedding 模型为什么必须重建索引？维度如何权衡？

<details>
<summary>参考答案</summary>

不同模型的向量空间完全不同（不同训练数据、不同维度）——新旧索引的向量不可比，混用会导致检索结果毫无意义。所以"换模型 = 删旧索引重建"是硬规则。

维度权衡：低维（如 512）语义表达能力够用、存储计算省；高维（如 1024）检索精度略高（约 3-5%）但成本翻倍。经验法则：**满足精度要求的前提下选最小维度**。

</details>

#### 4-5 🔴 中英混合文档（如 API 文档里的英文字段名 applyId / requestNo）对 embedding 模型有什么要求？

<details>
<summary>参考答案</summary>

必须用**多语言模型**（如 BGE 系列是中英双语训练的）。如果只用纯中文模型，英文 token 会被当作无意义内容处理，检索质量显著下降。

产品需求是中文、接口文档混着英文接口名的场景，多语言 embedding 是"必需品"不是"加分项"。

</details>

## 五、向量持久化（选型视角）

#### 5-1 🟢 主流向量数据库有哪些形态？各自适用场景？

<details>
<summary>参考答案</summary>

**1. 专用向量库**：Milvus / Pinecone / Weaviate（支持混合搜索）/ Qdrant（payload 过滤强）。性能功能最专，但需独立部署、自己处理数据一致性。

**2. 数据库扩展（插件）**：pgvector（PostgreSQL）/ MongoDB Atlas / Redis。复用现有库，向量+传统 SQL 结合，运维成本低；超大规模性能不如专用库。
→ pgvector 额外价值：支持 SQL 查询、检索审计、事务一致性、RBAC 权限——这是它相对轻量库的核心生产优势。

**3. 云厂商托管**：AWS OpenSearch / Azure AI Search / Vertex AI。和自家云生态深度集成、企业级合规与 SLA；但成本高、有厂商锁定风险。

**4. 轻量 / 嵌入式**：Chroma / FAISS（纯库非数据库）/ LanceDB。嵌入应用进程，开发体验好；适合原型、小项目、本地测试。

**简化选型**：Demo/原型 → Chroma、LanceDB；已有 PostgreSQL 且量不大 → pgvector；生产大数据量需独立部署 → Milvus、Qdrant；不想管运维 → Pinecone；深度绑定某云 → 对应云服务；要向量+关键词混合 → Weaviate、Qdrant。

本项目选择 Chroma 单链路，对应第 4 类。其他类别用于通用选型比较，不代表当前仓库实现。

</details>

## 六、向量检索

#### 6-1 🟢 一次完整的向量检索流程包含哪些步骤？

<details>
<summary>参考答案</summary>

```
查询文本 → embedding(查询) → 元数据过滤限定范围 → 向量距离计算
→ Top-K 排序 → 距离阈值过滤 → 可信证据 → 打包成 LLM 输入上下文
```

</details>

#### 6-2 🟡 元数据过滤为什么必须在 Top-K 之前执行？（见 1-6，从检索实现视角再答一次）

<details>
<summary>参考答案</summary>

先过滤（`WHERE 主体='X'`）再 Top-K，搜索空间先限定。反例：全库 Top-K 返回 12 条其中 10 条是其他主体的，应用层再过滤只剩 2 条，丢了本该召回的；更危险的是忘了过滤会把不相关主体内容当证据喂给 LLM。先过滤让"没搜到"成为明确空结果。

</details>

#### 6-3 🟡 距离阈值（max_distance）的作用？调大 / 调小分别有什么影响？

<details>
<summary>参考答案</summary>

过滤掉"看似相关实则无关"的候选——Top-K 返回的最相似 K 条不代表都足够相似，只是没有更相似的。

- 调大：候选 / 证据更多，但**引入噪音**（不相关内容混进来当证据）
- 调小：证据更精，但可能空结果（fail-on-empty 阻断），错失边缘相关的内容

阈值不是固定常数——换 embedding 模型 / 维度后必须重新调。

</details>

#### 6-4 🔴 "无证据时必须阻断、不能继续调 LLM"这条设计，防的是什么？

<details>
<summary>参考答案</summary>

防**幻觉**。无证据时若继续调 LLM，模型会在没有任何依据的情况下编造答案。

正确行为：返回"无法回答"模板 / 提示调整查询或放宽阈值，而不是把空上下文丢给 LLM 让它自由发挥。这是防止幻觉的最后一道防线，也是 RAG 系统必备的 fail-safe。

</details>

## 七、LLM 结构化抽取

#### 7-1 🟢 JSON Schema 在结构化抽取中的作用？`strict: true` 的含义？

<details>
<summary>参考答案</summary>

JSON Schema 定义抽取结果的**完整结构契约**——顶层必填字段、每个字段的类型 / 枚举 / 嵌套结构。

`strict: true` = 拒绝 Schema 之外的字段，防止 LLM 自由发挥加字段，保证输出结构稳定、可被下游程序消费。

</details>

#### 7-2 🟡 为什么结构化抽取的结果要区分"候选 / 已批准 / 未解决"等状态？为什么 LLM 不能自己批"已批准"？

<details>
<summary>参考答案</summary>

- 候选：机器提议，等人工确认
- 已批准：人工逐字段核对后签字放行
- 未解决：机器也无法确定（证据不足 / 冲突），必须阻断

LLM 的抽取**可能出错**（把选填当必填、接口读反、字段映射错）。如果 LLM 能自己批已批准，等于绕过了人工把关，错误会直接流进下游。所以原则：**机器只能提议，人签字才算数**。

</details>

#### 7-3 🟡 抽取结果的"证据对象"（来自哪份文档 / 定位在哪 / 原文摘录）有什么用？缺了原文摘录会怎样？

<details>
<summary>参考答案</summary>

每条业务结论必须带证据溯源：来自哪份文档、定位在哪、原文摘录是什么。

缺原文摘录的后果：审批人拿到候选结果，想核对"这条字段映射对不对"，但没有原文可对照——审批变成盲签。原文摘录是人工审批的唯一核对依据。

</details>

#### 7-4 🔴 防止 LLM 幻觉一般有几层机制？各层阻止什么？

<details>
<summary>参考答案</summary>

| 层级（教学归类，非官方术语） | 核心手段 | 解决什么 |
|---|---|---|
| 数据层 | RAG、知识库治理 | 知识错误、过时 |
| Prompt 层 | 明确指令、边界设定 | 过度自信 |
| 生成层 | 低 temperature、约束解码（structured output / JSON Schema） | 随机编造、输出结构不可控 |
| 校验层 | Fact-check、Self-critique | 漏检的错误 |
| 交互层 | 置信度、溯源、人工复核 | 用户端风险兜底 |

> **实践重点**：没有任何一层能 100% 消除幻觉。通常把 **RAG + Prompt 约束 + 输出校验** 组合使用性价比最高；金融等高风险场景再加**人工审核**这道最后防线。
>
> 本项目落点：数据层 = 带证据编号的 RAG；生成层 = temperature=0 + strict JSON Schema；交互层 = 人工审批（候选/已批准/未解决三态）+ 原文摘录溯源。

</details>

#### 7-5 🔴 temperature=0 为什么对结构化抽取重要？不设为 0 会怎样？

<details>
<summary>参考答案</summary>

temperature 控制输出的随机性。结构化抽取要的是**确定性**——同一份输入应该得到一致的抽取结果。

temperature 高时：同一份文档抽两次，字段映射可能不同 → 下游审批和代码生成依赖的输入不稳定，无法复现问题。设为 0 让"这次抽的结果 = 下次抽的结果"，这是生产可复现性的基础。

</details>

## 八、人工审批（理念）

#### 8-4 🔴 human-in-the-loop（人在环）为什么在金融场景是必须的？

<details>
<summary>参考答案</summary>

字段映射错误在金融场景可能造成**实际资金损失**（请求字段名写错、必填项缺失、方向写反）。AI 自主决策 = 错误无人把关。

正确做法：LLM 只能提议（候选），人工逐字段对照原文核对后签字（已批准），并记录审批人 / 时间 / 范围——出了差错能追责："这条是谁批的、他对照了什么证据"。

</details>

## 二、文档解析（实现）

#### 2-4 🔴 DOCX 解析为什么要按文档顺序交错处理段落和表格？

<details>
<summary>参考答案</summary>

DOCX 内部段落（`<w:p>`）和表格（`<w:tbl>`）按 XML 顺序交叉排列。如果先读完所有段落再读表格，就丢失了"这段文字描述的就是下面那个表"的位置关系。

代码上通过遍历 `doc.element.body` 依次判断 tag 是 `p` 还是 `tbl`，分别处理（`unified_parser.py`）。

</details>

## 三、文本切块（实现）

#### 3-3 🔴 chunk_id 为什么用确定性哈希生成？好处是什么？

<details>
<summary>参考答案</summary>

```python
chunk_seed = f"{document}|{locator}|{index}|{piece}"
chunk_id = f"chunk_{sha256(chunk_seed)[:24]}"
```

同一文档同一位置的 chunk，无论跑多少次生成的 chunk_id 都不变 → **索引幂等**：重复建库不会产生重复记录（配合 `uniquify_chunk_ids` 和 pgvector 的 `ON CONFLICT DO UPDATE`）。

</details>

## 五、向量持久化（实现细节）

#### 5-2 🟡 `knowledge_chunks` 表为什么同时有 metadata JSONB 列和 institution 等独立列？这叫什么设计？

<details>
<summary>参考答案</summary>

**反范式化（denormalization）**——读性能优化。

- JSONB 列：灵活，任意结构都能存，但查询慢（要解析 JSON）
- 独立列（institution / operation / content_type 等）：可以建 B-tree 索引，`WHERE institution='AURORA_DEMO'` 走索引毫秒级

设计 = 高频过滤字段独立建列 + 低频 / 新字段存 JSONB，两者兼顾。两种索引都有（独立列的 B-tree + metadata 的 GIN）。

</details>

#### 5-3 🟡 `ON CONFLICT (chunk_id) DO UPDATE` 解决什么问题？没有它会怎样？

<details>
<summary>参考答案</summary>

解决**索引幂等性**：同一文档重复建库不产生重复记录。

没有它，第二次索引同样的 chunk_id 会触发主键冲突 → 事务回滚 → 索引失败。有了它，重复写入变成"原地更新"（content / embedding / metadata 刷新）。生产环境索引脚本可能因网络抖动、参数调整重跑，不能每次手动清表。

</details>

#### 5-4 🔴 检索审计三张表（retrieval_runs / retrieved_candidates / accepted_evidence）解决了什么问题？

<details>
<summary>参考答案</summary>

让每次检索**完全可回溯**——"当时 LLM 看到了什么证据、为什么采纳 / 拒绝某条"。

- `retrieval_runs`：一次检索的完整记录（查询文本、过滤条件、embedding 配置）
- `retrieved_candidates`：每条候选的 chunk_id 和距离
- `accepted_evidence`：通过阈值的证据

金融场景下如果因字段映射错误产生资金差错，审计需要回答"这条字段是谁在何时基于什么证据批的"。这是轻量向量库没有、数据库扩展独有的生产级能力。

</details>

#### 5-5 🔴 pgvector 的 `vector` 类型和 `double[]` 的区别？`<=>` 运算符是什么？为什么建 extension 需要 DBA？

<details>
<summary>参考答案</summary>

- `vector` 是 pgvector 扩展定义的专用类型，支持距离运算符和索引（HNSW / IVFFlat）；`double[]` 只是普通数组，无法做向量索引和相似度计算
- `<=>` 是**余弦距离**运算符；还有 `<->`（欧氏距离）、`<#>`（负内积，返回值越小即越接近 -1，越相似）。检索 SQL：`ORDER BY embedding <=> '[0.1,...]'::vector LIMIT 12`
- `CREATE EXTENSION vector` 需要超级用户权限（本项目真实踩坑：业务用户建会报 permission denied）——所以必须 DBA 先建 extension，业务用户只建表读写

</details>

## 六、向量检索（实现细节）

#### 6-5 🔴 索引和检索的 embedding 配置校验在本项目哪里实现？校验失败说明什么？

<details>
<summary>参考答案</summary>

- Chroma：`rag_retrieve.py`，比对每个 chunk metadata 里的四项配置（provider/model/dimension/normalize）

## 八、审批闸门（实现）

#### 8-1 🟢 `--require-approved` 开关的作用？不传和传了的区别？

<details>
<summary>参考答案</summary>

- **不传**：只做结构校验（字段齐全、类型正确、枚举合法），允许 status = 候选
- **传了**：闸门落下——任何 status 不等于已批准的条目都报错，阻断代码生成

这是历史 M0 映射结构的审批闸门示例。当前主链路由 `derive_code_model.py` 拒绝非 approved 契约，再由 `validate_code_model.py` 校验派生模型。

</details>

#### 8-2 🟡 历史 M0 的 validate_mapping.py 做了哪几类校验？它为什么不能代替当前闸门？

<details>
<summary>参考答案</summary>

1. **结构校验**：每类对象必填字段齐全（variables 缺 used_by_operations 报错）
2. **枚举校验**：status 三态、mapping_direction 三方向、confidence 0-1
3. **交叉引用校验**：variables 引用的 operation 必须存在于 operations 列表
4. **禁用字段校验**：禁止 transformation_code / java_code 等自由格式代码字段
5. **未解决值校验**：institution / document_version 不能是 "unknown" 等未解决值

它校验的是旧 `synthetic_mapping.json` 结构，不能识别当前完整 approved 契约及 `code_model` 的操作、映射引用和模式约束，所以不能作为当前生成准入证明。

</details>

#### 8-3 🟡 "引用的 operation 不存在"这类交叉引用校验解决什么问题？

<details>
<summary>参考答案</summary>

防止 LLM **自相矛盾**——LLM 有时会在 variables 里引用一个 operations 里不存在的操作名（或者拼写不一致）。这类引用完整性校验让 JSON 内部"指得通"，避免下游代码生成时引用空操作。

</details>

#### 8-5 🔴 当前项目审批环节的真实状态是什么？（请诚实回答）

<details>
<summary>参考答案</summary>

**技术闸门和离线人工评审产物已存在，但不是线上审批系统**：

- 闸门机制是真的：`--require-approved` 硬编码 + 测试覆盖（喂候选断言报错）
- 仓库保留完整 11 操作候选契约和人工修订后的 approved 契约，均为 synthetic 数据
- 审批动作是离线逐字段核对，没有 UI、登录身份、权限或不可抵赖签名

准确表述："当前证明的是候选→人工修订→approved→确定性闸门这条离线链路；尚未实现多人线上审批系统。"

</details>

## 九、综合与工程化（实现细节）

#### 9-2 🟡 如果新增一家合成机构，完整的操作步骤是什么？

<details>
<summary>参考答案</summary>

1. 准备并在 `fixtures/manifest.yaml` 登记合成产品需求和 API 文档
2. 解析、切块、索引并检索，得到 `accepted_evidence` 和稳定 `chunk_id`
3. `llm_extract_integration_spec.py` 基于编号证据生成候选契约
4. 人工逐字段核对 evidence；确认项改为 approved，不确定项保留 unresolved
5. `derive_code_model.py` 从 approved 契约确定性派生 `code_model`
6. `validate_code_model.py` 校验操作和映射引用
7. `assemble_augmented_context.py` 装配证据目录、公共映射和对应模式范例
8. `[可选实验] code_synth_agent.py` 复制指定的已知合成范例，只逐方法改写 `FundManagerImpl`，再运行 Maven/契约测试
9. 生成并运行 `generation_trace.json` 校验，再执行 golden 评估和人工复核

</details>

#### 9-5 🔴 简述代码生成、追溯与契约测试

<details>
<summary>参考答案</summary>

**代码生成实验**（`code_synth_agent.py`）：读取 approved 契约派生的 `code_model`、编号证据、公共映射和对应模式的合成范例，先复制范例工程，再调用真实 LLM 逐个改写 `FundManagerImpl` 方法体。其他 Java 文件来自范例，因此不能称为完整 SPI 生成。

**追溯校验**：每个方法必须包含 `Evidence/Mapping` 注释；`generation_trace.json` 保存方法 hash、E 编号、稳定 chunk ID、文档定位和 M 编号，手工修改代码后 hash 不一致会失败。

**契约与 golden 测试**：Maven/JUnit 验证接口行为，golden 评估验证契约操作完整性和关键业务特征；人工复核仍是最终批准步骤。

</details>
