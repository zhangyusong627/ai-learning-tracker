## 3. 当前学习主线

当前主线是从 Java 工程师转向 AI 应用开发。Week 6 已完成，Week 7 的金融机构接入 Skill 已完成三模式 LLM 直写闭环；下一阶段优先补 RAG 量化评估，不重新学习已完成的 RAG 基础。

RAG 已经学习和确认过的关键链路：

```text
离线索引阶段：
原始文档
-> 文档解析和清洗
-> Embedding（向量化）
-> 落库前数据校验
-> 持久化到向量数据库
-> 数据准确性校验

在线问答阶段：
用户问题
-> 网关 API
-> 身份校验
-> 问题 Embedding
-> 带权限、版本等过滤条件的 Top-K 检索
-> 相关性阈值校验
-> 形成 accepted_evidence（最终可采纳证据）
-> 上下文组装和引用编号
-> Prompt（提示词）组装
-> 调用 LLM（Large Language Model，大语言模型）
-> LLM 输出校验
-> 返回答案或拒答
```

关键术语约定：

- `retrieved_candidates`：Top-K 检索阶段返回的候选结果。
- `accepted_evidence`：经过相关性阈值、权限、版本等校验后，最终允许进入 Prompt 的证据。
- 候选结果不等于最终证据。
- metadata filter（元数据过滤）应在 Top-K 检索前应用，例如权限、机构、产品、版本。
- 如果没有 `accepted_evidence`，应在调用 LLM 前拒答，不应让 LLM 猜。
- 离线索引阶段和在线问答阶段必须使用完全一致的 Embedding 模型，包括版本、配置、维度等。

用户对 RAG 的几个稳定理解：

- 相关性阈值放宽可能提升有答案问题命中率，但会降低查准率，并降低无答案问题的正确拒答率。
- 不能只看单一指标，要同时看召回率、命中率、查准率、无答案正确拒答率、上下文长度、检索成本等。
- 如果 Top-K 的 K 不变，阈值只影响候选结果进入最终证据的数量，不会改变 Top-K 阶段的排序结果。
- 权限不匹配应在进入 LLM 前拦截。
- 版本过滤应在 Top-K 检索前应用，而不是先全库检索再过滤。
- 文档版本未完整构建完成时，不应直接切到新版本，应通过灰度、原子切换和保留旧版本完成发布。

## 6. 资金网关业务背景的脱敏总结

用户之前负责过一个资金网关类系统，内部简称 GFW。这里不要展开公司内部细节，只保留公开表达层面的抽象：

- 系统定位：平台与多家第三方金融机构之间的统一接入、订单流转、事件编排和治理层。
- 业务目标：把平台侧用户流量导入不同金融机构产品，支持放款、还款等业务动作。
- 复杂性来源：机构数量多，产品线多，接入文档格式多，接口流程、字段、加解密、回调、异常处理和性能要求不同。
- 共性：大多数机构接入存在统一流程和模板化结构。
- 差异：每家机构在协议、字段、状态映射、签名加密、回调和特殊业务规则上存在个性化适配。

GFW 与 GFW-SPI 的抽象边界：

- GFW：统一订单、事件、调度、治理、状态流转和平台通用能力。
- GFW-SPI（Service Provider Interface，服务提供者接口）：每个机构自己的适配插件层，负责机构差异化接入逻辑。

Skill 项目的核心价值：

- 不是简单练习 AI 代码生成。
- 真正要解决的是“机构接入骨架重复开发、文档理解成本高、人工遗漏风险高、标准流程沉淀困难”的业务问题。
- 目标是生成覆盖大部分标准场景的接入骨架，让开发人员集中处理少量差异化逻辑和最终确认。

## 7. 机构接入 Skill 应生成什么

目标不是生成完整平台，也不是直接生成可上线代码，而是生成一个“可编译、可测试、可追溯、可人工确认”的完整合成 Java SPI 代码包。

建议输出内容：

- 新机构 SPI 模块目录。
- Maven/Gradle 模块声明和依赖占位。
- `FundManager` 或类似统一接口的完整合成实现。
- `META-INF/services` 或等价服务注册文件。
- 机构元数据配置，例如机构编码、产品编码、支持流程、接口清单。
- EventFlow（事件流）或流程编排骨架。
- 请求 DTO、响应 DTO、回调 DTO。
- HTTP 客户端封装。
- 签名、验签、加密、解密适配器的合成实现或受控调用。
- 外部状态码到内部状态码的映射。
- 异常分类和重试策略。
- 单元测试和契约测试样例。
- 人工确认清单：哪些字段、接口、异常、回调、幂等、资方特殊规则必须人工确认。

不应生成：

- 公司内部真实字段、真实机构名、真实密钥、真实 URL、真实 IP。
- 可直接连接真实机构的代码。
- 对原 GFW 公共核心模块的大规模改造。
