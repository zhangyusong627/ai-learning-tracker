## 核心数据流

```text
文件输入
→ 识别真实类型
→ 分发到对应解析器
→ 提取正文与结构
→ 统一为 Document
→ 解析质量校验
→ Documents + ParseResult
```

## 当前费曼解释

- 文件能打开不代表解析成功，因为正文可能为空、乱码、顺序错误或 metadata 缺失；
- 扫描型 PDF 可以打开但没有文本层，应进入 OCR，而不是直接判定文件损坏；
- 不同解析器必须统一输出 `Document`，否则下游切分和 Embedding 需要维护大量格式分支；
- `page` 只适合页面稳定的 PDF，Word 应使用 `block_index` 等结构位置；
- 普通资料允许部分入库时必须显式标记 `partial`，合同等高风险文档存在缺页时应阻止入库。
- 单个文件解析异常应记录为 `failed`，不能中断整个批处理任务。
- 文件级解析状态和缺失位置必须复制到每个 `Document.metadata`，否则进入切分和向量入库后会丢失完整性信息。

## 四个核心职责

### 1. Document

代表一段可供切分、Embedding 和检索使用的正文，由 `page_content` 和 `metadata` 组成。一份文件可以生成多个 `Document`。

### 2. ParseResult

代表整份文件的一次解析报告。一份文件对应一个 `ParseResult`，其中包含多个 `Document`，以及整体状态、警告和质量指标。它解决了空 `Document` 列表无法区分“空内容、格式不支持、需要 OCR、文件损坏、解析失败”的问题。

### 3. 解析质量状态

| 状态 | 含义 |
|---|---|
| `success` | 完整成功 |
| `partial` | 部分成功 |
| `ocr_required` | 需要 OCR |
| `empty` | 未提取到内容 |
| `skipped` | 类型不支持或无法识别 |
| `failed` | 解析过程异常 |

生产版本可进一步拆分为 `execution_status`、`completeness` 和 `next_action`，避免单个状态无法同时表达“部分成功且需要 OCR”。

### 4. 入库策略

解析器只报告事实，入库策略结合业务风险作出最终决定：普通资料可按规则允许 `partial`，合同和安全规程等高风险文档只允许完整且质量校验通过的内容进入正式知识库。

记忆类比：`Document` 是可用货物，`ParseResult` 是整批质检报告，质量状态是质检结论，入库策略是仓库放行规则。

## 真实文件类型识别

扩展名可以被误设或人为修改，不能作为唯一依据。识别顺序为：

```text
扩展名提示
→ Magic Number 初步识别
→ 容器内部结构校验
→ 对应解析器验证
→ 记录扩展名与真实类型冲突
```

- PDF 常见文件签名：`%PDF-`；
- DOCX：ZIP/`PK` 容器内包含 `word/document.xml`；
- XLSX：ZIP/`PK` 容器内包含 `xl/workbook.xml`；
- PPTX：ZIP/`PK` 容器内包含 `ppt/presentation.xml`。

Magic Number 只能初步识别类型，不能证明文件完整、安全或可成功解析。生产环境通常使用 Apache Tika、Magika 等成熟工具，不继续手工维护完整规则；业务系统仍需负责格式白名单、大小限制、安全扫描、解析器路由和异常策略。

## 三层测试

### 1. 概念理解：补讲后通过

学习者起初不了解 `ParseResult` 的职责。补讲“一份文件对应一个 ParseResult、包含多个 Document”后，能够解释空 `Document` 列表无法表达解析失败原因。

### 2. 代码诊断：通过

独立发现 PDF 加载器把 `status` 硬编码为 `success` 的错误；指出存在空页时正确状态应为 `partial`，并需要判断 OCR 或其他异常原因。

### 3. 场景迁移：补充门禁后通过

面对包含关键规则截图的银行制度 Word，学习者识别出需要 OCR 且不能标记为完整成功；经一次提示后补充高风险文档必须阻止部分入库。

## 独立决策任务

面对扩展名错误、扫描 PDF、损坏文件和不同完整性要求的批量入库场景，学习者独立提出：

- 先识别真实类型，不能只按扩展名分发解析器；
- PDF 空页需要进一步 OCR 和审核；
- 单文件异常需要记录并继续批处理；
- 普通宣传资料可按业务规则允许部分内容入库，但必须保留异常状态；
- 安全操作规程必须保证顺序和语义完整，缺失内容时阻止入库并转人工修复。

该决策已落实为 `can_index(result, require_complete)` 入库门禁。

## 持续误区与修正

- `extracted_pages` 的含义一度不清楚，属于英文术语障碍，不是状态逻辑障碍；后续首次出现英文指标时同步给出中文释义。
- 曾用 `status: success` 解释成功原因，补讲后能够依据总页数、成功页数和空页列表解释状态。
- 起初不了解 `ParseResult`，通过物流质检类比建立了文件级报告与内容级对象的职责边界。
- `ppt/presentation.xml` 对应的是 PPTX，不是旧版二进制 PPT。
- 初版把 `BadZipFile` 转成 `None`，会将损坏文件误分类为 `skipped`；修正为向上抛出，由统一入口记录为 `failed`。
- 初版异常分支只根据扩展名填写 `file_type`，在扩展名错误且解析失败时会污染日志；修正为优先保留已识别的真实类型。
- 逐行阅读中再次发现 `continue` 与 `break` 的作用混淆，已修正为：`continue` 只跳过当前循环，`break` 才结束整个循环。
- `extraction_method="ocr"` 表示 OCR 已执行并产生当前正文，不表示“等待 OCR”；等待动作应由 `next_action` 表达。
- 当前代码阅读断点：`print_result()` 中的 `result.warnings or "无"`；`main()` 与 `if __name__ == "__main__"` 尚未讲解。
