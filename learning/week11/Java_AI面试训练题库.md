# 第一部分：Java（60 题）

## A. Java 基础与集合（J01～J08）

### J01【必背】HashMap 的底层结构和 put/get 流程是什么？

- 评分点：数组、链表/红黑树、hash 定位、equals、树化条件、负载因子和扩容。
- 追问：为什么容量是 2 的幂？为什么树化阈值是 8 且容量至少 64？
- 参考答案：JDK 8 的 HashMap 由数组、链表和红黑树组成。put 先扰动 hash，再用 `(n-1)&hash` 定位桶，冲突后比较 hash 与 equals；链表达到 8 且数组至少 64 时树化。元素超过容量乘 0.75 后通常扩容为两倍，get 走相同定位后在链表或树中查找。
- 练习记录：尚未练习。

### J02【必背】ConcurrentHashMap 如何保证并发安全？

- 评分点：JDK 8 桶级 synchronized、CAS、volatile、并发扩容、读操作特点。
- 追问：为什么读通常不加锁？它和 Hashtable 的锁粒度有什么区别？
- 参考答案：JDK 8 使用 CAS 完成空桶初始化或计数更新，桶内冲突更新时锁住桶头节点；Node 的关键字段通过 volatile 保证可见性。扩容时用 ForwardingNode 标记并允许线程协助迁移。Hashtable 锁住整张表，而 ConcurrentHashMap 的锁粒度更细。
- 练习记录：尚未练习。

### J03【必背】ArrayList 和 LinkedList 应该怎么选？

- 评分点：底层结构、随机访问、插入删除、内存占用、缓存局部性。
- 追问：为什么 LinkedList 中间插入不一定比 ArrayList 快？
- 参考答案：ArrayList 是动态数组，随机访问 O(1)，尾部追加快，中间增删需要搬移；LinkedList 是双向链表，按下标访问 O(n)，定位节点后增删 O(1)。实际开发通常优先 ArrayList，因为内存连续、遍历快、额外对象开销小；LinkedList 只有在已经持有节点位置且频繁增删时才可能有优势。
- 练习记录：尚未练习。

### J04【重点】HashMap 为什么线程不安全？

- 评分点：并发 put 覆盖、size 不准、JDK 7 扩容成环、JDK 8 仍不安全。
- 追问：为什么不能用 Collections.synchronizedMap 代替所有 ConcurrentHashMap 场景？
- 参考答案：HashMap 没有同步控制，并发 put 可能覆盖节点、丢数据或使计数不准确；JDK 7 头插扩容还可能形成环，JDK 8 改为尾插也没有获得线程安全。并发读写应使用 ConcurrentHashMap，不能因为某次测试没复现就认为安全。
- 练习记录：尚未练习。

### J05【重点】HashMap 的扩容机制是什么？

- 评分点：触发阈值、容量翻倍、JDK 8 高位判断、原位置或旧容量偏移。
- 追问：已知预计元素数时，初始容量怎么估算？
- 参考答案：元素数超过阈值 `capacity * loadFactor` 时触发 resize，通常把容量扩为两倍。JDK 8 不必重新计算完整 hash，节点根据旧容量对应的那一位是 0 还是 1，留在原索引或移动到“原索引+旧容量”。预估数据量时应提前设置足够容量，降低多次扩容成本。
- 练习记录：尚未练习。

### J06【重点】`==`、`equals` 和 `hashCode` 有什么关系？

- 评分点：引用比较、逻辑相等、equals/hashCode 契约、哈希集合行为。
- 追问：只重写 equals 不重写 hashCode 会出现什么问题？
- 参考答案：基本类型的 `==` 比值，引用类型的 `==` 比是否同一对象；equals 表达逻辑相等。两个对象 equals 为 true 时 hashCode 必须相同，否则 HashMap/HashSet 可能把逻辑相等对象放入不同桶，导致查找或去重异常；hashCode 相同则不代表 equals 一定相同。
- 练习记录：尚未练习。

### J07【重点】String 为什么不可变？StringBuilder 和 StringBuffer 怎么选？

- 评分点：final/内部状态、字符串池、安全性、线程安全、性能。
- 追问：不可变对象为什么更适合做 HashMap 的 key？
- 参考答案：String 的值创建后不能修改，修改会产生新对象，这使它适合常量池复用、缓存 hash，并减少并发和安全风险。频繁单线程拼接用 StringBuilder；需要共享可变字符串且必须同步时才考虑 StringBuffer。String 不可变也保证作为 key 后 hash 不会改变。
- 练习记录：尚未练习。

### J08【背景相关】Java SPI 的加载机制、优点和缺点是什么？

- 评分点：ServiceLoader、META-INF/services、接口与实现解耦、懒加载/遍历、类加载器。
- 追问：业务上的“SPI 接入包”和 Java SPI 机制有什么区别？
- 参考答案：Java SPI 通过 `META-INF/services/接口全限定名` 注册实现类，ServiceLoader 在运行时借助线程上下文类加载器发现并实例化实现。它符合开闭原则，适合插件扩展，但原生机制需要遍历加载、缺少命名选择和完善依赖管理。业务 SPI 是平台定义的接入接口与实现包，是否使用 Java ServiceLoader 是另一层技术选择。
- 练习记录：尚未练习。

## B. JVM（J09～J16）

### J09【必背】JVM 运行时内存区域如何划分？

- 评分点：程序计数器、虚拟机栈、本地方法栈、堆、方法区/元空间、线程私有与共享。
- 追问：栈溢出和堆溢出的典型原因分别是什么？
- 参考答案：程序计数器、虚拟机栈和本地方法栈是线程私有；堆和方法区是线程共享。对象实例主要在堆中，栈帧保存局部变量、操作数栈和返回信息，JDK 8 后类元数据主要放在本地内存的元空间。递归过深可能 StackOverflow，持续创建且无法回收对象可能导致堆 OOM。
- 练习记录：尚未练习。

### J10【必背】JVM 如何判断对象可回收？常见 GC 算法是什么？

- 评分点：可达性分析、GC Roots、标记清除、复制、标记整理。
- 追问：哪些对象可以作为 GC Roots？
- 参考答案：JVM 从 GC Roots 做可达性分析，不可达对象才进入回收流程。GC Roots 包括线程栈引用、类静态字段、常量和 JNI 引用等。年轻代常使用复制思想，老年代根据回收器使用标记清除或标记整理；不同算法在停顿、吞吐和碎片之间取舍。
- 练习记录：尚未练习。

### J11【重点】CMS、G1 和 ZGC 的主要差异是什么？

- 评分点：目标、堆布局、停顿、并发阶段、适用场景，不背绝对结论。
- 追问：为什么不能脱离 JDK 版本、堆大小和延迟目标谈回收器选型？
- 参考答案：CMS 面向低停顿但存在碎片和并发失败问题，已从新版本移除；G1 把堆划分为 Region，按收益回收并提供停顿目标；ZGC 通过并发标记、转移和着色指针等技术追求超低停顿。选型要结合 JDK 版本、堆规模、吞吐和延迟目标，并用 GC 日志与压测验证。
- 练习记录：尚未练习。

### J12【必背】类加载过程和双亲委派机制是什么？

- 评分点：加载、验证、准备、解析、初始化；委派顺序；安全和避免重复。
- 追问：Java SPI 为什么会使用线程上下文类加载器？
- 参考答案：类生命周期核心阶段是加载、验证、准备、解析和初始化。双亲委派先让父加载器尝试加载，父加载器无法完成时子加载器再处理，避免核心类被替换并减少重复定义。SPI 需要由核心库发现应用类路径中的实现，因此会借助线程上下文类加载器形成反向可见能力。
- 练习记录：尚未练习。

### J13【必背】常见 OOM 类型及线上排查流程是什么？

- 评分点：heap、metaspace、direct buffer、native thread；日志、jstat、dump、MAT、引用链。
- 追问：线上发生 OOM 时为什么不能不加判断就执行大体积 heap dump？
- 参考答案：先根据异常信息区分 Java heap space、Metaspace、Direct buffer memory 或无法创建本地线程等类型，再检查 GC 日志、内存曲线和进程资源。必要时获取 heap dump，用 MAT 查看支配树和到 GC Roots 的引用链。生产操作要评估磁盘、停顿和进程状态，不能为了取证放大故障。
- 练习记录：尚未练习。

### J14【重点】线上 CPU 飙高或接口突然变慢怎么排查？

- 评分点：监控定界、进程/线程、jstack、nid 转换、GC、慢 SQL、下游依赖。
- 追问：线程大量 BLOCKED、WAITING、RUNNABLE 分别说明什么方向？
- 参考答案：先看监控确定时间、实例和资源维度，再用 top 找进程与高 CPU 线程，把线程 ID 转为十六进制并在 jstack 中定位调用栈。同时检查 GC、线程池、慢 SQL、连接池和外部依赖延迟。接口慢不等于 CPU 高，必须用证据逐层缩小范围。
- 练习记录：尚未练习。

### J15【重点】年轻代、老年代、Minor GC 和 Full GC 的关系是什么？

- 评分点：对象分配、Eden/Survivor、晋升、分配担保、Full GC 风险。
- 追问：大对象和长期存活对象什么时候进入老年代？
- 参考答案：新对象通常先在 Eden 分配，年轻代回收后存活对象在 Survivor 间复制并增加年龄，满足年龄、动态年龄或空间条件后晋升老年代。Minor GC 主要处理年轻代，Full GC 通常影响整个堆并带来更长停顿。具体布局和行为与所用回收器有关，不能把固定比例当成所有 JVM 的事实。
- 练习记录：尚未练习。

### J16【重点】内存泄漏与内存溢出有什么区别？

- 评分点：不可回收引用、容量不足、关系、常见泄漏源、排查证据。
- 追问：线程池环境中的 ThreadLocal 为什么容易形成泄漏？
- 参考答案：内存泄漏是对象已无业务用途却仍被引用，长期积累可能最终触发内存溢出；内存溢出则是申请资源时确实无法满足。常见泄漏源有无界缓存、静态集合、未释放监听器、连接和 ThreadLocal value。应通过持续增长曲线、dump 对比和引用链确认，而不是只看一次内存占用。
- 练习记录：尚未练习。

## C. 并发编程（J17～J26）

### J17【必背】synchronized 的实现原理是什么？

- 评分点：对象监视器、字节码、对象头、可重入、互斥和可见性、版本差异。
- 追问：实例方法、静态方法和代码块分别锁谁？
- 参考答案：同步方法通过 ACC_SYNCHRONIZED 标志，代码块通过 monitorenter/monitorexit 实现，锁关联到对象监视器。它既保证互斥，也建立进入和退出监视器的 happens-before 关系。实例方法锁 this，静态方法锁 Class 对象，代码块锁显式指定对象；锁优化细节要结合具体 JDK 版本。
- 练习记录：尚未练习。

### J18【必背】volatile 能保证什么，不能保证什么？

- 评分点：可见性、有序性、内存屏障、不保证复合操作原子性。
- 追问：为什么 volatile 能用于双重检查单例，但不能保证 `i++` 安全？
- 参考答案：volatile 保证一个线程写入后其他线程能看到，并限制相关指令重排，但不能把读—改—写复合操作变为原子操作。双重检查中的实例引用使用 volatile，是为了防止“分配、初始化、赋值”重排导致看到半初始化对象；`i++` 仍需锁或原子类。
- 练习记录：尚未练习。

### J19【必背】线程池核心参数和任务提交流程是什么？

- 评分点：core、max、queue、keepAlive、factory、handler；核心→队列→最大→拒绝。
- 追问：为什么不建议直接使用 Executors 创建固定线程池？
- 参考答案：任务到来时先创建到 corePoolSize；核心线程满后进入工作队列；队列满后再扩容到 maximumPoolSize；仍无法处理则执行拒绝策略。生产中应显式设置有界队列、线程命名和拒绝策略，避免无界队列导致内存堆积或无界线程导致资源耗尽。
- 练习记录：尚未练习。

### J20【重点】线程池大小应该如何估算和验证？

- 评分点：CPU/IO 类型、等待与计算比例、下游容量、压测、隔离。
- 追问：快慢接口共用一个线程池会出现什么问题？
- 参考答案：CPU 密集型通常接近核心数，IO 密集型可根据 `核心数 × (1 + 等待时间/计算时间)` 做初始估算，但公式只是起点。最终要结合响应时间、队列长度、拒绝数、CPU 和下游连接池压测。不同延迟和优先级任务应做线程池隔离，避免慢任务拖死关键链路。
- 练习记录：尚未练习。

### J21【重点】ThreadLocal 的原理和内存泄漏风险是什么？

- 评分点：ThreadLocalMap、弱引用 key、强引用 value、线程池复用、remove。
- 追问：为什么 key 是弱引用仍然可能泄漏？
- 参考答案：每个线程持有自己的 ThreadLocalMap，Entry 的 key 弱引用 ThreadLocal，但 value 仍被 Entry 强引用。在线程池中线程长期存活，key 被回收后 value 可能继续滞留，因此必须在 finally 中 remove。它适合线程内上下文，不是跨线程自动传递方案。
- 练习记录：尚未练习。

### J22【重点】死锁的四个必要条件是什么，如何排查和预防？

- 评分点：互斥、占有等待、不可剥夺、循环等待；jstack；锁顺序、超时、缩短范围。
- 追问：数据库死锁与 JVM 线程死锁的排查证据有什么不同？
- 参考答案：四个必要条件同时满足才会死锁。JVM 中可通过 jstack 查找线程互相等待的锁环；预防方式包括统一加锁顺序、减少嵌套、缩小临界区和使用 tryLock 超时。数据库死锁则应查看数据库死锁日志、事务 SQL 和锁记录，不能只看 Java 栈。
- 练习记录：尚未练习。

### J23【重点】AQS 和 ReentrantLock 的核心原理是什么？

- 评分点：volatile state、CAS、CLH 变体队列、park/unpark、公平与非公平。
- 追问：非公平锁为什么通常吞吐更高？
- 参考答案：AQS 用 volatile state 表示同步状态，获取失败的线程进入 FIFO 等待队列并 park，释放时唤醒后继。ReentrantLock 在此基础上实现可重入、公平或非公平策略。非公平锁允许新线程先尝试抢占，减少上下文切换，但可能让排队线程等待更久。
- 练习记录：尚未练习。

### J24【重点】CAS 的原理、ABA 问题和适用边界是什么？

- 评分点：比较交换、CPU 原子指令、自旋、ABA、版本号、竞争成本。
- 追问：为什么高竞争场景下 CAS 不一定比锁快？
- 参考答案：CAS 只有在内存值等于期望值时才原子更新，失败者通常自旋重试。ABA 指值从 A 变 B 又回 A，单纯比较值无法感知中间变化，可用版本戳解决。竞争激烈时大量自旋会浪费 CPU，因此无锁不等于在任何场景都更高效。
- 练习记录：尚未练习。

### J25【重点】CountDownLatch、CyclicBarrier 和 Semaphore 有什么区别？

- 评分点：一次性倒计数、可循环栅栏、并发许可、应用场景。
- 追问：主线程等待多个机构查询任务完成应该选哪个？
- 参考答案：CountDownLatch 让一个或多个线程等待 N 个任务完成，计数不能重置；CyclicBarrier 让一组线程在栅栏点互相等待并可重复使用；Semaphore 用许可数量限制并发访问。主线程等待多个独立任务汇总通常使用 CountDownLatch 或更现代的 CompletableFuture 组合。
- 练习记录：尚未练习。

### J26【重点】CompletableFuture 做异步编排时有哪些风险？

- 评分点：线程池选择、异常传播、超时、阻塞 join、上下文传递、任务取消。
- 追问：为什么不应把所有异步任务都扔进 commonPool？
- 参考答案：CompletableFuture 适合并行调用和依赖编排，但必须显式考虑执行器、异常链、超时与降级。默认 commonPool 可能被慢 IO 占满并影响其他业务；join/get 位置不当又会把异步变回阻塞。生产中应使用隔离线程池，并通过 exceptionally、handle、orTimeout 等方式处理失败边界。

## D. 数据库（J27～J36）

### J27【必背】MySQL 索引为什么使用 B+ 树？

- 评分点：多叉、树高、磁盘 IO、叶子链表、范围查询、与哈希/红黑树比较。
- 追问：为什么非叶子节点不存整行数据？
- 参考答案：B+ 树分支多、树高低，单次查询需要的磁盘页访问少；数据集中在叶子节点，叶子按顺序通过链表连接，既支持等值也支持范围查询。非叶子只保存索引键和指针，可以在一个页内容纳更多分支。哈希不擅长范围查询，红黑树分支少导致树高更高。

### J28【必背】聚簇索引、二级索引、回表和覆盖索引是什么？

- 评分点：InnoDB 主键叶子整行、二级索引叶子主键、回表、覆盖。
- 追问：为什么主键过长会放大所有二级索引？
- 参考答案：InnoDB 聚簇索引的叶子节点保存完整行，二级索引叶子保存索引列和主键值。通过二级索引拿到主键后再查聚簇索引叫回表；查询所需列都能从二级索引得到则是覆盖索引。因为每个二级索引都携带主键，过长主键会增加索引空间和 IO。

### J29【必背】事务 ACID 和四种隔离级别是什么？

- 评分点：原子、一致、隔离、持久；脏读、不可重复读、幻读；数据库默认差异。
- 追问：一致性是数据库单独保证的吗？
- 参考答案：原子性保证事务整体成功或失败，隔离性控制并发可见，持久性保证提交结果留存，一致性是业务约束在事务前后成立的最终目标，需要数据库机制与应用规则共同保证。隔离级别从读未提交到串行化逐步增强，并依次限制脏读、不可重复读和幻读，但实现与默认值要结合具体数据库。

### J30【必背】InnoDB 的 MVCC 如何工作？

- 评分点：隐藏事务字段、undo log 版本链、Read View、快照读与当前读。
- 追问：RC 与 RR 下 Read View 创建时机有什么差异？
- 参考答案：InnoDB 通过记录中的事务信息和回滚指针连接 undo log 版本链，快照读根据 Read View 判断哪个版本可见，从而实现读写并发。RC 通常每次语句创建 Read View，RR 通常在事务首次一致性读时创建并复用。`select ... for update`、update 等当前读读取最新记录并加锁。

### J31【重点】MySQL 的行锁、间隙锁和 next-key lock 有什么关系？

- 评分点：锁住索引记录、区间、记录加区间、防幻读、索引条件影响。
- 追问：查询没有命中索引时，为什么锁范围可能超出预期？
- 参考答案：记录锁锁定索引记录，间隙锁锁定记录之间的区间，next-key lock 是二者组合，用于 RR 下限制范围内插入。InnoDB 的行锁本质上锁索引，具体范围受索引、查询条件和隔离级别影响；没有合适索引时扫描和加锁范围可能扩大。

### J32【重点】一条慢 SQL 应该如何系统排查？

- 追问：SQL 已经使用索引为什么仍然可能很慢？

### J33【重点】联合索引的最左前缀和常见索引失效场景是什么？

- 追问：WHERE 条件书写顺序会决定联合索引能否使用吗？
- 参考答案：联合索引按列顺序建立有序结构，查询通常要从最左列形成可利用的连续前缀。函数、隐式类型转换、前导 `%` 和不合适的范围条件可能降低可用性，但“失效”不能只背规则，应以执行计划和优化器成本判断。现代优化器通常会重排等值条件，书写顺序不是核心。

### J34【背景相关】PostgreSQL 与 InnoDB 的 MVCC 有什么主要差异？

- 评分点：PG 行版本、xmin/xmax、dead tuple、vacuum；InnoDB undo 版本链。
- 追问：PG 为什么会表膨胀？长事务有什么影响？
- 参考答案：InnoDB 主要通过 undo log 维护旧版本并用 Read View 判断可见性；PostgreSQL 把多版本行保留在表数据中，通过 xmin/xmax 判断可见性，再由 vacuum 回收死元组。长事务会阻止旧版本被清理，造成膨胀和事务 ID 风险，因此要监控 vacuum 与长事务。

### J35【背景相关】PostgreSQL 的 WAL 和 vacuum 分别解决什么问题？

- 评分点：预写日志、崩溃恢复、持久性；死元组回收、统计信息、VACUUM FULL 风险。
- 追问：普通 VACUUM 和 VACUUM FULL 有什么差异？
- 参考答案：WAL 要求数据页落盘前先记录日志，用于崩溃恢复和复制，是持久性基础；vacuum 回收 MVCC 产生的死元组空间并维护可见性信息。普通 vacuum 通常复用空间但不把文件立即缩小，VACUUM FULL 重写表并需要更强锁，生产使用要谨慎。

### J36【背景相关】资金金额应该使用什么数据类型，如何处理精度和单位？

- 评分点：数据库 NUMERIC/DECIMAL、Java BigDecimal、统一最小单位、舍入规则、禁止 double。
- 追问：BigDecimal 为什么建议用字符串构造？equals 和 compareTo 有何差异？
- 参考答案：数据库使用 NUMERIC/DECIMAL 或明确约定的最小货币单位，Java 使用 BigDecimal，不能用 float/double 承载资金。金额转换必须明确元/分方向、精度和舍入模式。`new BigDecimal("0.1")` 避免二进制浮点误差；equals 比较值和 scale，数值比较通常使用 compareTo。

### J37【必背】Spring IOC 和 Bean 生命周期是什么？

## F. Redis、消息队列与分布式（J45～J52）

### J45【必背】缓存穿透、击穿和雪崩分别是什么？

- 评分点：不存在数据、热点失效、大量同时失效；空值/布隆、互斥/逻辑过期、随机过期/降级。
- 追问：布隆过滤器为什么会误判但不会漏掉已加入元素？
- 参考答案：穿透是持续查询不存在数据，可缓存空值或用布隆过滤器；击穿是热点 key 失效瞬间回源，可用互斥重建、逻辑过期；雪崩是大量 key 同时失效或缓存整体不可用，要打散过期时间、限流降级并提高可用性。方案需同时考虑一致性与恢复风暴。
- 练习记录：尚未练习。

### J46【必背】Redis 分布式锁如何正确实现？

- 评分点：SET NX PX 原子、唯一 value、Lua 释放、租期、续期、业务幂等。
- 追问：业务执行超过租期或发生主从切换怎么办？
- 参考答案：获取锁用带过期时间的原子 SET NX，value 保存唯一持有者标识；释放时用 Lua 原子校验 value 后删除。长任务需要合理租期或续期，但分布式锁不能替代业务幂等与数据库约束。故障切换下仍有一致性边界，强一致场景应评估协调服务或 fencing token。

### J47【重点】如何保证缓存与数据库的一致性？

- 评分点：Cache Aside、先更新库再删缓存、失败重试、延迟双删局限、CDC、最终一致。
- 追问：数据库提交成功但删除缓存失败怎么办？
- 参考答案：常用 Cache Aside：读未命中回源并写缓存，写时先提交数据库再删除缓存。删除失败要通过消息重试、事务消息或 CDC 订阅变更补偿，并监控不一致窗口。缓存和数据库通常无法简单双写成强原子，应根据业务定义可接受的一致性级别。

### J48【重点】Redis 为什么快，哪些操作会让它变慢？

- 追问：Redis 6 引入多线程后还能说它是单线程吗？
- 参考答案：Redis 主要依靠内存访问、高效数据结构、事件驱动和避免命令执行锁竞争获得高性能。所谓单线程主要指核心命令执行路径，网络 IO、持久化等并非都单线程。大 key、全量扫描、复杂命令、fork 和网络拥塞都会造成延迟抖动。

### J49【重点】如何保证消息“不丢、不重、尽量有序”？

- 追问：为什么工程上通常实现 at-least-once 加消费幂等，而不是迷信 exactly-once？
- 参考答案：生产端等待可靠确认，Broker 做持久化和副本，消费端业务成功后再确认或提交位点；失败重试会带来重复，因此消费逻辑必须用业务唯一键或状态机幂等。同一订单需要有序时按业务键路由到同一队列/分区并串行消费，全局有序通常代价过高。

- 追问：为什么多层服务都重试会形成重试风暴？

# 第二部分：AI 大模型应用（40 题）

## A. LLM 与 Prompt 基础（A01～A07）

### A01【必背】Token 和上下文窗口是什么，为什么会影响成本与效果？

- 评分点：分词单元、输入输出共同占窗、模型/编码器差异、截断、成本、RAG/摘要。
- 追问：为什么不能把中文字符数直接当成 token 数？
- 参考答案：Token 是模型分词器处理和计费的基本单元，不等同于汉字或英文单词；不同模型分词方式不同。上下文窗口限制一次请求中系统提示、历史、检索证据和输出的总 token。超限应通过检索、摘要、窗口管理和裁剪解决，并用目标模型 tokenizer 实测。
- 练习记录：尚未练习。

### A02【重点】Temperature、Top-P 和 Top-K 如何影响生成？

- 评分点：随机性、候选截断、不要机械同时调、代码/结构化低随机、评测验证。
- 追问：低 temperature 能否保证代码完全确定？
- 参考答案：Temperature 调整概率分布尖锐程度，Top-P 保留累计概率内候选，Top-K 限定最高概率的 K 个候选。结构化抽取和代码生成通常降低随机性，但参数含义受供应商实现影响，低温也不等于绝对确定；还需要 schema、约束、测试和固定模型版本。
- 练习记录：尚未练习。

### A03【了解】Transformer 自注意力解决了什么问题？

- 评分点：Q/K/V、相关性加权、并行、长距离依赖、平方复杂度边界。
- 追问：多头注意力为什么不是简单重复计算？
- 参考答案：自注意力把每个 token 映射为 Query、Key、Value，通过 Query 与 Key 的相关性对 Value 加权，使每个位置动态聚合上下文。多头让模型在不同表示子空间关注不同关系。它易于并行并擅长长距离依赖，但标准注意力随序列长度呈平方级时间和显存开销。

### A04【必背】提示词工程能解决什么，不能解决什么？

- 评分点：角色/任务/边界/格式/示例、降低歧义、不能补知识和确定性、版本化。
- 追问：什么时候应该改 Prompt，什么时候应该加确定性代码？
- 参考答案：Prompt 能明确任务、输入边界、步骤、示例和输出格式，降低歧义并引导模型行为；但不能保证事实正确、严格业务约束或弥补缺失知识。可解释的软行为可迭代 Prompt，金额计算、权限、审批和格式校验等硬约束应交给程序、schema 和测试。

### A05【重点】复杂业务中的 Prompt 如何版本管理和动态组装？

- 评分点：模板与变量分离、版本号、变更记录、测试集、灰度、回滚、敏感输入隔离。
- 追问：只在 Git 中保存 prompt 文本为什么还不够？
- 参考答案：系统提示、任务模板、示例和动态证据应分层组装，每次请求记录 prompt 版本、模型、参数和输入摘要。变更需用固定评测集回归，必要时灰度和回滚。仅保存文本无法复现实验，还需要关联模型版本、参数、检索结果和输出校验版本。

### A06【必背】如何稳定得到符合业务规范的 JSON/XML？

- 评分点：结构化输出/JSON Schema、字段说明、解析校验、业务校验、重试修复、禁止只靠示例。
- 追问：schema 校验通过是否代表业务正确？
- 参考答案：优先使用模型原生结构化输出或 Tool Calling 的 JSON Schema，明确必填字段、类型、枚举和禁止额外字段。输出后先做语法/schema 校验，再做金额、状态和跨字段业务校验；失败可有限重试或进入人工。格式正确只证明结构合法，不证明事实有证据或业务语义正确。

### A07【重点】Prompt Injection 是什么，RAG 场景如何防御？

- 评分点：不可信内容携带指令、指令与数据隔离、权限最小化、工具白名单、输出校验、人工审批。
- 追问：检索到的内部文档为什么也不能默认可信？
- 参考答案：提示词注入是让不可信输入伪装成指令，诱导模型越权或泄露数据。应把系统指令与文档数据明确隔离，限制模型工具权限、参数和可访问数据，对输出做白名单校验，关键动作必须人工审批。RAG 文档也可能被污染，因此检索来源、权限和内容都要治理。

## B. RAG 与评估（A08～A20）

### A08【必背】标准 RAG 的完整链路是什么？

- 评分点：解析、切块、embedding、存储、查询、过滤、召回、重排、阈值、生成、引用、评估。
- 追问：离线链路和在线链路的失败点分别有哪些？
- 参考答案：离线链路把文档解析为结构化块，切分、向量化并连同 metadata 入库；在线链路对问题处理后先做权限/metadata 过滤，再召回、融合或重排，经过证据阈值形成上下文，最后让 LLM 基于证据生成并输出引用。解析质量、索引版本、召回和生成必须分别评估。
- 练习记录：尚未练习。

### A09【重点】文档解析和 Chunk 切分如何影响 RAG？

- 评分点：标题/表格/页码结构、语义完整、大小/重叠、父子块、可追溯 metadata。
- 追问：为什么固定字符数切分容易破坏金融接口文档？
- 参考答案：解析必须保留标题层级、表格行列、页码和来源位置，否则字段与含义会错位。Chunk 太小会丢上下文，太大则召回不精确并增加 token；应按接口、章节和表格等业务结构切分，必要时使用父子块或适度重叠，同时复制可追溯 metadata。
- 练习记录：尚未练习。

### A10【必背】Embedding 是什么，如何选择 Embedding 模型？

- 评分点：文本到稠密向量、语义相似、语言/领域、维度、长度、归一化、离线评测。
- 追问：更高维是否一定检索更好？
- 参考答案：Embedding 把文本映射到向量空间，使语义相近内容距离更近。选型要看中英文和领域效果、最大长度、向量维度、推理成本及许可证，并用自己的黄金查询评测。维度更高只代表表示容量和存储成本变化，不保证任务效果更好。
- 练习记录：尚未练习。

### A11【重点】向量数据库和关系数据库有什么区别，怎么选？

- 评分点：相似搜索、ANN 索引、metadata 过滤、事务/SQL、规模、运维；Chroma/pgvector边界。
- 追问：为什么项目原型使用 Chroma，不代表生产一定继续用它？
- 参考答案：向量系统以距离搜索和近似最近邻索引为核心，关系库擅长结构化约束、事务和精确查询；pgvector 把二者结合在 PostgreSQL 中，Chroma 更适合本地原型和可复现实验。选型应看数据量、过滤、并发、权限、备份和现有运维，不应只按“专用库更专业”决定。
- 练习记录：尚未练习。

### A12【必背】为什么检索前要先做 metadata 过滤？

- 评分点：机构/版本/文档类型/权限、缩小候选、串库风险、过滤在向量召回前。
- 追问：先全库向量召回再过滤有什么风险？
- 参考答案：metadata 过滤先限定租户、机构、文档版本、接口和发布状态，保证后续向量检索只在合法候选中进行。先全库召回再过滤既浪费 Top-K 名额，也可能产生越权或跨机构证据污染。权限过滤尤其必须在检索前完成。
- 练习记录：尚未练习。

### A13【必背】Top-K、相关性阈值和 accepted_evidence 应如何配合？

- 评分点：候选与采纳分离、分数方向、阈值权衡、无证据策略、审计。
- 追问：为什么不能把向量库返回的 Top-K 全部喂给 LLM？
- 参考答案：Top-K 只是 retrieved_candidates，必须先确认距离或相似度分数方向，再通过相关性、事实锚点和业务规则形成 accepted_evidence。阈值宽会引入噪声，严会漏召回，应通过评测调参。accepted_evidence 为空时应先执行拒答/待确认策略，不能让 LLM 自行补全。
- 练习记录：尚未练习。

### A14【重点】向量召回、BM25 和混合检索怎么选？

- 评分点：语义、精确词、字段名/错误码、并行召回、融合、评测。
- 追问：金融接口文档为什么尤其需要关键词召回？
- 参考答案：向量召回擅长语义近似，BM25 擅长字段名、接口路径、错误码等精确词。金融接入同时需要二者，可并行召回后通过 RRF 或学习排序融合，再按业务证据过滤。是否增加混合检索应由黄金查询中的 Bad Case 证明，而不是为了架构复杂。
- 练习记录：尚未练习。

### A15【重点】Rerank 和 RRF 分别解决什么问题？

- 评分点：候选重排、跨编码器精度与成本、RRF 基于排名融合、分数不可直接比。
- 追问：为什么不同召回器的原始分数不宜直接相加？
- 参考答案：RRF 按各召回列表中的名次融合，不依赖不同系统分数尺度，适合合并向量和 BM25；Reranker 对查询—文档对做更精细相关性判断，通常更准但增加延迟和成本。常见流程是多路召回、RRF 合并，再对较小候选集重排。
- 练习记录：尚未练习。

### A16【必背】Hit@K、Precision@K、Recall@K 和 MRR 怎么算？

- 评分点：至少命中、前K正确比例、相关证据召回比例、首个正确排名倒数。
- 追问：Hit@5 100% 为什么仍可能检索质量很差？
- 参考答案：Hit@K 判断前 K 是否至少有一条正确证据；Precision@K 是前 K 中正确证据比例；Recall@K 是应召回证据中实际召回比例；MRR 取第一条正确结果排名的倒数再平均。Hit 很高但 Precision 很低，说明正确证据被大量噪声包围，仍可能误导生成。
- 练习记录：尚未练习。

### A17【重点】无答案问题应该如何处理和评估？

- 评分点：accepted_evidence 为空前置拦截、拒答/待确认、无答案集、拒答率与误拒率。
- 追问：一味提高拒答率为什么不等于系统更安全？
- 参考答案：检索和证据支持不足时，应在调用 LLM 前返回“证据不足”或进入人工确认，不能依靠提示词要求模型别编。评测要同时包含有答案与无答案样本，关注正确拒答、错误作答和误拒答。全部拒答虽然安全但没有业务价值。
- 练习记录：尚未练习。

### A18【重点】如何建立 RAG 的黄金集和回归评测？

- 评分点：代表性查询、相关证据标注、无答案、独立保留集、版本记录、Bad Case 分类。
- 追问：为什么参与调参的15条查询不能继续充当唯一泛化证据？
- 参考答案：黄金集应覆盖主要文档、查询类型、精确字段、语义表达和无答案场景，并标注期望证据。每次切块、模型、索引和阈值变化都固定回归；参与调参的数据会产生过拟合，因此还需要独立保留集。Bad Case 要区分解析、召回、排序、过滤和生成原因。
- 练习记录：尚未练习。

### A19【必背】RAG 与微调如何选择？

- 评分点：外部知识 vs 行为能力、更新、可追溯、成本、组合使用。
- 追问：资方 API 文档为什么优先 RAG 而不是微调？
- 参考答案：RAG 适合频繁更新、需要引用和权限控制的外部知识；微调适合改变模型稳定行为、风格或特定能力，不适合把持续变化文档硬写进权重。资方文档要求版本化和可审计，因此优先 RAG；若输出行为长期不稳定，可在足够数据和评测基础上考虑微调。

### A20【重点】长文档和长上下文应该如何处理？

- 评分点：结构切分、检索、层级摘要、查询改写、lost in the middle、成本与缓存。
- 追问：上下文窗口足够大时为什么仍可能需要 RAG？
- 参考答案：长文档应按结构切分并检索相关证据，复杂问题可查询拆解、父子检索或分层摘要。即使窗口能装下全文，无关信息仍会稀释关键证据，产生中间信息遗失并增加成本与延迟。长上下文是容量能力，不等于检索和可追溯问题自动解决。

## C. Agent 与 AI 工程化（A21～A30）

### A21【必背】Agent 和 Workflow 有什么区别？

- 评分点：固定编排 vs 动态决策、确定性、可审计、适用场景、人审。
- 追问：金融代码生成为什么不应该让 Agent 自主决定所有步骤？
- 参考答案：Workflow 的步骤和分支由程序预先定义，结果更可预测；Agent 由模型根据状态动态选择工具和下一步，灵活但不确定。金融场景应把解析、审批、编译和测试放进确定性 Workflow，仅在需要语义判断或生成时使用模型，并限制工具和人工审批。

### A22【重点】ReAct Agent 的工作机制和风险是什么？

- 评分点：推理—行动—观察循环、工具、终止条件、循环/成本/注入/错误传播。
- 追问：如何防止 Agent 无限调用工具？
- 参考答案：ReAct 让模型根据当前状态选择行动，应用执行工具后把观察结果返回，再继续决策直到结束。工程上要设置最大步数、超时、预算、工具白名单、参数校验和终止条件，并保存轨迹。模型推理文本不能当作可信审计结论，关键动作仍需确定性验证。

### A23【必背】Function Calling / Tool Calling 的原理是什么？

- 评分点：模型输出工具名和结构化参数、应用执行、结果回传、模型不直接执行、校验授权。
- 追问：模型生成了合法 JSON，为什么仍不能直接执行转账工具？
- 参考答案：应用把工具描述和参数 schema 提供给模型，模型返回调用意图与参数；真正执行由应用完成，再把结果交回模型。应用必须校验参数、权限、幂等和风险，不能把模型输出当授权。高风险工具需要人工确认和审计。

### A24【重点】MCP、RAG、Agent 和 Tool Calling 的关系是什么？

- 评分点：MCP 标准连接协议、RAG 知识模式、Agent 决策者、Tool Calling 调用机制，避免混淆。
- 追问：接入 MCP 是否意味着系统已经是 Agent？
- 参考答案：RAG 是检索外部知识增强生成的应用模式；Tool Calling 是模型表达工具调用的机制；Agent 是动态决策和循环执行的控制方式；MCP 是把工具、资源和提示以统一协议暴露给模型应用。使用 MCP 只说明连接标准化，不代表一定采用 Agent 自主循环。

### A25【重点】多轮对话如何保证上下文一致性？

- 评分点：会话状态、消息裁剪、摘要、长期记忆检索、事实源、并发版本、隐私。
- 追问：为什么不能把所有历史消息永久塞进上下文？
- 参考答案：短期历史可使用滑动窗口，较长会话用结构化摘要，长期事实存入可检索记忆并标注来源与时间。关键业务状态应来自数据库而非模型记忆；并发消息要有会话版本和顺序控制。无限追加历史会超窗、增加成本并放大旧错误与注入风险。

### A26【重点】为什么模型调用层要可配置、可切换？

### A27【重点】大模型应用如何优化成本？

### A28【重点】如何降低 LLM API 延迟？
