## 第一部分：项目叙事（必考，10 分钟版核心）

### Q1. 用 3 分钟介绍你这个项目
**答题要点**：
- 一句话定位：**用检索增强的方式，把"金融机构接入文档"自动翻译成可编译、可测试的 Java 接入代码**——解决助贷行业里每家资方接入都要人工写一遍 SPI 的重复劳动。
- 两条主线：① 离线索引（解析文档→切块→向量化→入库）② 在线生成（检索证据→喂大模型→直写代码→人工复核→编译测试闭环）。
- 核心卖点（背熟）：**大模型全程不读原始文档，只读检索回来的证据**——这是防幻觉的关键设计。
- 背景优势只讲可公开的通用经验：理解 Java SPI、机构差异适配、字段映射和接入验证；公司名、机构数量和内部实现按本人确认的披露口径另行准备。

### Q2. 为什么说"约定优于配置"是你这个项目的核心洞察？
**答题要点**：
- 三家合成机构验证了共性流程与差异分层：协议传输、数据字段、业务逻辑是独立维度，直连/断直连/混合属于链路编排维度。
- 所以：差异是表面的，约定是本质的。大模型生成代码时"识别约定变体→检索对应模式→填充特有字段→生成→校验"。
- 三种接入模式（直连/断直连/混合）的差异在**事件流编排**，加密、对账格式等业务细节是另一个维度。

### Q3. 你的项目里人工审核（Human-in-the-loop）是什么角色？为什么必须有？
**答题要点**：
- 三层闸门：① 契约候选→人工确认（approved 才生成）② 生成代码→人工逐行复核清单 ③ 编译/契约/golden 测试兜底。
- 理由：金融场景错误成本极高（错一个字段映射 = 放款出错 = 资损/合规风险）。**AI 提效 + 人定责**，这是金融行业的底线，也是和"全自动生成"方案的本质区别。
- 诚实边界：这套方案不是生产级全自动；仓库证明的是合成链路、追溯和测试结果，不证明未经核验的生产提效比例。

### Q4. 你如何用可核验数据证明项目有效？
**答题要点**：
- 只引用仓库证据：恒誉 11 操作、云腾 10 操作、衡丰 11 操作；golden 报告分别运行 18、14、16 个测试并通过。
- RAG、契约派生、方法级追溯和 Skill 格式都有可复现命令。
- 耗时、覆盖率等真实工作指标若要写简历，必须先确认样本口径、计时边界和可披露范围，不能用作品集测试结果替代。

## 第二部分：RAG 技术深挖（作品集技术核心，9.4 周五重点）

### Q5. 你的检索增强（RAG）链路是怎么设计的？为什么大模型不直接读文档？
**答题要点**：
- 链路背熟：文档 → 统一解析（ParseResult：成功/部分成功/OCR 需求/失败）→ 切块 → embedding 向量化 → 向量库（Chroma + PostgreSQL/pgvector 双实现）→ 检索（metadata 过滤 + Top-K）→ **业务相关性阈值过滤**（低于阈值的证据不采用）→ 编号证据 E1…En 喂大模型。
- 为什么不让大模型直接读原文：① 原文太长超上下文 ② 无关内容会干扰（幻觉来源）③ 证据可追溯（哪段文档支撑哪条映射，能查）。
- 关键点：**LLM 只读检索证据，不读原始文档**——面试官最爱问这个，答出"防幻觉 + 可审计"就到位。

### Q6. 你说的"阈值过滤"是什么？低了会怎样，高了会怎样？
**答题要点**：
- 检索出来 Top-K 条证据后计算距离；本项目是**距离越小越相关，高于距离阈值才丢弃**。
- 距离阈值设得过宽：垃圾证据混进来；设得过严：好证据被误杀。必须用量化评估联合调整 Top-K、阈值和切块策略。
- 你的实现里有 accepted_evidence 的落库审计——每条被采用的证据都有记录，能回溯。

### Q7. 检索质量你怎么评估？Hit rate / MRR 这些指标怎么算？
**答题要点**：
- Hit rate（命中率）：问题检索出的 Top-K 里有没有包含正确答案。
- MRR（平均倒数排名）：正确答案排在第几位——第一 1.0，第二 0.5，第三 0.33，取平均。
- 当前项目只完成 RAG 功能与安全路径验证，尚未形成 Hit@K/MRR/Recall@K 的量化报告；这是下一阶段明确缺口，不能说已经评估检索准确率。

### Q8. 向量检索和关键词检索（BM25）你会怎么选？有没有做混合检索？
**答题要点**：
- 向量检索：懂语义，"授信申请"和"credit apply"能匹配，但对精确字段名、编号类不敏感。
- BM25：精确匹配好，但不懂语义。
- 金融接入场景里**字段名精确匹配很重要**（字段名错一个就废了），所以理想是混合检索（hybrid）：向量召回 + 关键词兜底，再合并去重排序。你的项目里以向量为主，这是一个可讲的"优化方向"（诚实：当前版本没做混合检索，作为下一步）。

### Q9. 你怎么防大模型幻觉？（至少答出 3 条）
**答题要点**：
- ① 检索增强：LLM 只读证据不读原文，答案必须有出处。
- ② 阈值过滤：低相似度证据直接丢弃，不给模型编造空间。
- ③ 人工确认闸门：契约、代码都要人批，机器不自动放行。
- ④ 确定性校验：代码生成后编译 + 契约测试 + golden 测试兜底——错代码编译不过。
- ⑤ 高置信也不能自动 approved；任何进入生成的业务事实都要人工确认。
- 加分：还做了"事实一致性校验"设计（确定性规则→长期小模型）——虽然作品集里是简化实现，但能讲出思路。

## 第三部分：代码生成（作品集核心玩法，9.3 周四重点）

### Q10. 你的"LLM 直写完整代码"和"模板生成"有什么本质区别？为什么弃用模板？
**答题要点**：
- 早期版本是"模板 + 空骨架 stub"（确定性的），你发现它对生产提效没意义——因为业务逻辑才是大头，骨架填空是表面功夫。
- 当前路径不使用模板引擎：输入是产品需求、API 文档、三家合成样例构造的 M001–M075 公共映射，以及三种合成模式范例。
- 本质区别：模板只能填预设占位符；LLM 直写能生成业务方法，但非确定性更高，所以必须增加证据追溯、人工复核、编译和测试。
- 诚实补充：直写带来不确定性（每次生成可能不同），所以配套人工复核 + 编译测试闭环。

### Q11. 你那个"符号事实清单"是什么？为什么大模型生成代码老自创类名？
**答题要点**：
- 大模型第一次生成时自创了 `CreditApplyResponseDTO`（实际类叫 `CreditApplyResponse`），编译失败。
- 解法：从范例包自动提取"符号事实清单"喂给大模型——真实的 DTO 类名 + setter 签名 + Constants 常量 + 辅助方法签名，**只准引用清单内的符号**。
- 这是 LLM 代码生成工程的通用经验：**给模型"合法符号边界"，别让它自由发明**。类似人类写代码时 IDE 的自动补全约束。

### Q12. 大模型生成代码你用什么测试兜底？"契约测试"和"golden 测试"区别？
**答题要点**：
- 先做追溯校验：方法必须声明 Evidence/Mapping，`generation_trace.json` 绑定稳定 chunk ID、原文定位和源码 hash；代码被手工改动后必须重新核验。
- 契约测试（Contract Test）：用模拟（mock）端点验证"生成的方法是否按契约做对事"——比如授信申请是否正确调了 credit/apply、是否把 applyId 写进 stage、错误码是否归一化。
- golden 测试：固定一组"标准答案特征"（比如 applyLoan 必须包含 requireStage、yuanToCent、route 计算），生成后逐条比对——防止模型这次生成的和上次行为不一致。
- 一句话：契约测试验证"对不对"，golden 验证"稳不稳"。

### Q13. 编译失败后你的"反馈重写"是怎么做的？
**答题要点**：
- 闭环：生成 → mvn 编译 → 失败则提取错误信息（含行号、错误类型）→ 反馈给大模型"上次编译错误是这些，请修正" → 重新生成 → 再编译，最多重试 N 轮。
- 踩过的坑（讲出来是亮点）：错误提取正则最初漏了"不兼容的类型"这类错误；大模型看到错误后可能越改越糟，所以要限制轮次。
- 这就是 LLM 编程工具（Cursor/Claude Code）的经典循环，你亲手实现过。

### Q14. 三种接入模式（直连/断直连/混合）在你的代码生成里怎么体现？
**答题要点**：
- 输入条件明确指定模式，大模型只生成 1 套对应模式的完整包（不是一次生成 3 套）。
- 直连：SPI 直接调用合成机构接口。
- 断直连：经合成中转通道调用机构接口。
- 混合：按合成路由标志选择直连或中转路径，示例响应回显 `route`。
- 强调：加密/还款通道/担保费/对账格式是**资方文档业务细节差异**（独立维度，不与接入模式绑定）——这是你修正过的认知，讲出来显专业。

## 第四部分：金融领域 + Java 基础（你的老本行，9.1-9.3 混合考）

### Q15. 什么是 SPI（服务提供接口）？Java 的 SPI 机制怎么用？
**答题要点**：
- 两个概念别混：① 平台接入规范里的"SPI 代码包"（业务概念：每个资方一个实现包）② Java SPI 机制（ServiceLoader：`META-INF/services/<接口全限定名>` 文件里写实现类，运行时按需加载）。
- 作品集里两者都用了：每个机构一个 `FundManagerImpl`（业务 SPI），并通过 `META-INF/services/<接口全限定名>` 注册实现类。
- 用 Java SPI 的好处：平台核心不感知具体机构，新增资方=新增一个实现包 + 注册文件，符合开闭原则。

### Q16. 你们平台怎么保证"一个方法只干一件事"？为什么这么设计？
**答题要点**：
- 合成范例里，FundManager 接口一个方法只对应**一个机构动作**（如 applyCredit/queryCredit），方法内只做"取参→组装→调机构一次→写 stage→返回 DTO"。
- 动作先后由**平台按事件流（eventFlow）驱动**：平台查 eventFlow() 知道下一步调谁；轮询由平台循环调 queryCredit（SPI 单次查询，不内部循环）。
- 跨动作传递靠 stage_result（applyCredit 写 credit.apply_id，signBind 写 bind.agreement_no，applyLoan 从 stage 校验前置）。
- 好处：SPI 无状态、可重试、可测试，平台完全掌控流程——这是金融系统稳定性的关键。

### Q17. 金融机构对接的"六维转换"是什么？举个例子
**答题要点**：
- 不是字段名对照表，是 6 种转换规则组合：① 字段名映射 ② 类型转换 ③ 格式转换 ④ 枚举值映射 ⑤ 条件逻辑 ⑥ 拆分合并。
- 例子（背熟一个）：用信金额——平台入参是元（`amount`），机构要分（`loanAmt`），要做"元→分 ×100"（yuan_to_cent）；查询返回时分转元（cent_to_yuan ÷100）。**方向反了就是放款金额差 100 倍的事故**。
- 枚举例子：同一合成业务状态在平台和机构侧可以使用不同编码，必须通过已批准映射显式转换，不能让 LLM 猜测。

### Q18. 你对账文件处理怎么做？为什么对账重要？
**答题要点**：
- 异步任务（平台 job 触发，不在实时事件流里）：D+1/D+2 拉取对账文件（恒誉 CSV、衡丰 Excel 3 sheet、云腾固定长度文本），核对当天放款/还款是否一致。
- 对账是异步接口之外的独立核对手段；回调和文件都可能失败，因此需要重试、完整性校验和差异处理，不能声称“对账文件不会丢”。
- 你的作品集里：对账下载可重试（E6001 对账文件未生成要重试），对账文件命名带机构前缀。

### Q19. 你项目里的加密是怎么处理的？（RSA / SM2 / AES-GCM+HMAC）
**答题要点**：
- 直连（恒誉）：RSA 签名（SHA256withRSA）+ 明文 XML/JSON。
- 断直连（云腾）：国密 SM2/SM4（JDK 模拟）。
- 混合（衡丰）：JSON + AES-GCM 加密 + HMAC 加签。
- 关键：**加密/签名统一在 Client 层做**（doCall 里组装报文→签名→发送），业务方法体不碰加密细节、不落明文密钥——密钥走配置变量。

### Q20. 如果机构接口超时了你会怎么处理？幂等怎么做？
**答题要点**：
- 超时处理必须按契约区分业务操作和文件任务；当前合成规则里业务操作不自动重试，只有特定对账下载错误允许重试。
- 幂等：申请类操作必须幂等——平台订单号（platformOrderNo/orderNo）作为幂等键，机构侧"同单号不重复创建"。你作品集的 stage 设计天然支持：applyCredit 产出的 applyId 写 stage，后续动作取 stage 不用重新触发。
- 查询兜底：不依赖回调，平台轮询 queryCredit/queryLoan 到终态——回调可能丢，轮询不会。

## 第五部分：架构与设计决策（9.3 周四 + 压力追问）

### Q21. 你这个项目最大的技术挑战是什么？你怎么解决的？
**答题要点**（选 1-2 个讲透）：
- 挑战一：三家合成样例覆盖 Markdown、DOCX 和 XLSX 等格式及不同字段结构。解决：统一解析器 + ParseResult 状态机（成功/部分成功/OCR 需求/失败）+ 标准文档块。
- 挑战二：大模型生成代码不可控（自创类名、类型错、参数键错）。解决：符号事实清单 + 空值保护规则 + 编译反馈重写循环——**一轮轮把规则沉淀进 prompt**。
- 挑战三：平衡"AI 提效"和"金融可审计"。解决：人工确认闸门 + 证据编号可追溯 + 编译测试兜底。

### Q22. 为什么用向量数据库，又为什么准备了 Chroma 和 pgvector 两套？
**答题要点**：
- 向量库存 embedding 向量 + 原文 + metadata，支持相似度检索。
- Chroma：本地轻量，快速验证用（作品集 demo 友好）。
- pgvector：PostgreSQL 扩展，适合需要 SQL 过滤、事务、权限和检索审计的部署。
- 选型取决于数据规模、基础设施和治理要求；本项目验证了 Chroma 与 pgvector 两条本地链路，不代表所有生产环境都应选 pgvector。

### Q23. 如果你的方案要上生产，还差什么？（诚实边界题，必考）
**答题要点**：
- ① 建立检索量化评估体系（当前尚无 Hit@K/MRR/Recall@K 报告）。
- ② OCR/图片字段识别（真实资方文档常带扫描件）。
- ③ 多机构灰度验证（当前 3 家合成机构，真实要几十家）。
- ④ 审计/合规加强（谁批的、批了什么、为什么，全链路留痕）。
- ⑤ 混合检索（向量+关键词）。
- 讲法：先承认边界，再讲"我知道差距在哪、下一步怎么做"——比硬吹强一万倍。

### Q24. 你项目里的数据都是合成的，面试官问"这算不算真实经验"怎么答？
**答题要点**：
- 三层区分：① 本人确认可披露的真实工作经验 ② 作品集可复现的合成验证 ③ 尚未实现的生产化设想。三者不能混写。
- 为什么用合成数据：红线要求——真实资方接口文档有版权和合规风险，不能用公司资料做个人作品集。**用合成数据同样能验证技术链路**（解析/检索/生成/测试全跑通），且不踩红线。
- 加分：你的"数据与知识产权政策"文档就是专门讲这个的，面试官问版权问题直接引用。

## 第六部分：AI 应用工程通用（9.4 周五 + 跨项目）

### Q25. 你用过哪些大模型？为什么要做模型可配置？
**答题要点**：
- 仓库可验证的是 DeepSeek 兼容调用路径；其他模型或编码工具的个人使用经历按本人确认后回答，不由本项目代为证明。
- 作品集里 `code_synth_agent.py` 通过环境变量配置 `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`——**模型可插拔**，不绑定厂商。
- 为什么重要：① 模型能力在快速变化，绑定一家有风险 ② 成本优化（不同任务用不同模型）③ 供应商切换无痛。
- 加分：你的 LLM 客户端是 OpenAI 兼容协议，任何兼容厂商（DeepSeek/OpenAI/国产）都能接。

### Q26. 提示词工程你在项目里做了哪些实践？
**答题要点**：
- 全项目提示词分两组四份：M1 抽取（system+user）、M2/M3 代码生成（system 9 条硬性纪律 + user 动态拼装 10 部件），完整清单见作品集 `docs/提示词清单.md`。
- 代码生成 system prompt 的 9 条纪律归 5 类：架构纪律（单动作、stage 传递）、符号边界（只用清单内类/常量）、数据转换（六维映射）、健壮性（空值保护、BigDecimal 全限定名）、可追溯性（Evidence/Mapping 注释 + 仅输出方法体）。
- 关键洞察：把编译和测试失败的根因固化进提示词或确定性校验——符号事实清单（防自创类名）、platform_param_key（防 request. 前缀）、状态码直传（防归一化分歧）、computed_in_spi（防 route 读响应）、retryable 默认 false（防错误码被重试）——提示词是从失败中迭代出来的，共 9 个版本。
- 结构化输出 + few-shot（贴范例包同名单动作方法作参考）+ 编译反馈重写循环（失败信息动态追加进 user prompt）。

### Q27. 你的系统里哪些环节用了大模型，哪些没用（确定性环节）？
**答题要点**：
- 用 LLM 只有两个环节：① 文档→结构化契约抽取（输出 candidate，AI 不能批准业务结论）② 已批准契约→代码生成（输出方法体，带 Evidence/Mapping 追溯注释）。
- 不用 LLM（确定性脚本）：文档解析、切块、向量化、检索、阈值过滤、契约派生 code_model、编译测试、golden 评估——确定性环节给可靠性兜底，LLM 环节给智能，这是 AI 工程的核心分工思维。

### Q28. 如果让你把这个系统做成真正的产品，产品形态是什么？
**答题要点**：
- 形态：一个"资方接入 IDE 插件 / CLI 工具 / 平台服务"——接入新机构时，上传文档 → 自动出契约 → 人工确认 → 自动生成代码包 → 联调测试 → 交付。
- 用户价值：缩短文档梳理和重复编码时间，同时用证据、审批和测试降低遗漏风险；具体节省比例需要真实样本测量。
- 商业模式/团队价值：机构接入是助贷平台的常态需求，每接入一家都是重复劳动，这个工具把重复劳动自动化。

## 第七部分：快问快答（每题 30 秒，练流利度）

| # | 问题 | 30 秒答案 |
|---|---|---|
| Q29 | RAG 是什么？ | 检索增强生成：先从知识库检索相关证据，再让大模型基于证据回答，解决大模型"不知道+瞎编"问题 |
| Q30 | embedding 是什么？ | 把文本转成向量（数字数组），语义相近的文本向量距离近，用于相似度检索 |
| Q31 | chunk（切块）多大合适？ | 几百到上千 token，太小丢上下文、太大检索不精准；按文档结构（段落/表格）切 |
| Q32 | 向量库和普通数据库区别？ | 向量库支持向量相似度检索（按语义找），普通库只支持精确匹配 |
| Q33 | 大模型为什么有幻觉？ | 训练数据外的不知道，靠"编"来回答；上下文太长/太杂也会误导 |
| Q34 | 流式输出了解吗？ | SSE/流式：模型逐 token 返回，用户看到打字机效果，适合对话/长输出 |
| Q35 | 上下文窗口是什么？ | 模型一次能处理的最大 token 数，超出会被截断，所以长文档要切块检索 |
| Q36 | 温度参数（temperature）是啥？ | 控制随机性：低=稳定保守（生成代码用 0.2），高=多样创新 |
| Q37 | 你项目里为什么用合成数据？ | 真实资方文档有版权/合规风险，红线不能用公司资料；合成数据同样能验证技术链路 |
| Q38 | Java 17 你用了哪些新特性？ | 记录类 record、switch 表达式、文本块、密封类；作品集 pom 是 Java 17 |
