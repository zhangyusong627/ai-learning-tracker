## 分：人工闸门（本次）

### 是什么
在 Agent 执行链路中，对高风险动作（写操作、资金变动、对外发送）插入一个"暂停点"，由人类审阅并显式批准 / 拒绝后，Agent 才继续。模型本身**不直接执行**高风险动作。

### 为什么需要
- 模型会出错（幻觉、误判）
- 高风险动作不可逆或代价大（真实扣款、发信、删数据）
- 合规 / 审计要求人类担责

### 标准实现模式（四步）
1. **动作分级（Action Classification）**：只读（safe，自动执行）vs 写操作 / 高风险（requires_approval）
2. **提案-确认-执行三段式（Propose-Confirm-Execute）**：Agent 生成"建议动作 proposal"（不执行）→ Harness 拦截并呈现 → 人类 approve / reject → 仅 approve 才由 Harness 执行
3. **确定性预校验（Deterministic Pre-check）**：执行前用硬编码规则先筛（金额上限、目标白名单）；规则拒绝的直接 fail，不进人工队列（节省人类注意力）
4. **审计轨迹（Audit Trail）**：记录谁、何时、批准了什么、执行结果、能否回滚

### 与你作品集的对应
`funding-gateway-ai-guardian`：
- `query_metrics` / `query_history` / `query_governance_rules` = 只读，自动执行
- `suggest_adjustment` / `generate_report` = 写操作，需人工审批
- 确定性安全规则校验 = 确定性预校验
- 模拟执行 + 审计 + 回滚 = 审计轨迹 + 回滚能力

### 失败案例（无闸门）
让模型自己执行写操作 → 幻觉出错误指令直接扣款 → 事故且不可审计。

## 分：错误处理（Error Handling）

### 是什么
Agent 调用工具或执行动作时会发生各种失败（工具超时、限流、返回空结果、异常报错、模型输出非法参数）。错误处理让 Agent 在这些情况下不崩溃、能恢复、能给出可控结果。

### 为什么需要
- 真实环境工具会失败（下游挂了、超时、限流）
- 模型会输出非法 / 不完整参数
- 不处理 → Agent 崩溃或无限重试烧钱

### 标准模式：按失败性质分类处理
1. **瞬时失败（Transient）**：超时、网络抖动、限流 → 可重试，带退避（backoff），并设最大重试次数封顶（防烧钱）
2. **永久失败（Permanent）**：参数非法、目标不存在、权限不足 → 不可重试，直接失败 + 上报 / 转人工
3. **空结果（Empty Result）**：工具返回成功但无数据 → 不致命，标记"信息缺失"，让模型换路径或显式说明
4. **执行类失败（Action Failure）**：写操作没做成 → 必须停 + 人工介入，不擅自重试（区别于查询类）
5. **兜底（Fallback）**：重试耗尽 → 降级（返回"无法完成"+原因）或转人工

### 与你作品集的对应
- 已有"失败恢复"思路（Layer 1）：查询类失败可重试 / 换工具，执行类失败必须停 + 人工
- 确定性预校验提前拦截"参数非法"（永久失败在进闸门之前就挡掉）
- 需补：重试退避、最大重试封顶、空结果处理

### 失败案例（无错误处理）
- 工具超时 → Agent 卡死或无限重试 → 烧 token 且不产出
- 模型输出非法参数（如负数金额）→ execute 抛异常 → 整个 Agent 崩溃

## 分：可观测性（Observability）

### 是什么
Agent 是黑盒循环——你不知道它调了什么工具、花了多少 token、卡在哪一步。可观测性给 Agent 加"仪表盘"，记录每步的决策、工具调用、耗时、token、错误，便于调试、复盘、成本核算、审计。

### 为什么需要
- Agent 循环出错难定位（黑盒）
- 成本控制依赖 token / step 统计
- 审计合规需要完整轨迹
- 线上问题复盘需要 trace

### 标准实现：三大支柱（Logs / Metrics / Traces）
1. **日志（Logs）**：离散事件记录（"调了 query_metrics""人工拒绝"）——demo 里的 audit_log 即日志
2. **指标（Metrics）**：聚合数值（总 token、平均步数、成功率、错误率、单次成本）——用于监控与成本核算
3. **追踪（Traces）**：一次任务内完整调用链（步骤1→工具A→步骤2→工具B→结束），含每步耗时 / token——用于定位卡点

### 与你作品集的对应
- 审计轨迹（audit trail）已做 = 日志 + 部分追踪
- 需补：指标（token 累计、step 计数、单次成本估算）、追踪（每步 span 耗时）
- Layer 4 demo 已展示 token 随步数增长（809→…→5197）——正是指标的价值

### 失败案例（无可观测性）
- Agent 线上跑飞（无限循环 / 重复调用），只看到账单暴涨，不知哪步卡了
- 用户投诉"答非所问"，无法复盘它当时调了什么工具、看到了什么

## 分：成本控制（Cost Control）

### 是什么
Agent 循环会累积 token 与步数（你 Layer 4 已看到 809→…→5197），且失控循环会烧钱。成本控制给 Agent 设"预算闸"，防止跑飞。

### 为什么需要
- Agent 循环可能无限 / 重复调用（Layer 1 失败案例：重复查 history 3 次）
- 强模型每次调用贵
- 线上多用户并发，成本放大

### 标准手段
1. **max_steps 兜底**：最大步数强制截断（Layer 1/4 已学）
2. **模型分层（Model Tiered Routing）**：简单任务（分类、路由）用便宜弱模型，复杂推理才用强模型——呼应 Layer 3 吴恩达"弱模型 + Agentic Workflow 常干过强模型零样本"
3. **缓存（Caching）**：相同 / 相似请求命中缓存不重复调模型（prompt caching / 结果缓存）
4. **上下文压缩（Compression）**：Layer 4 学的 compaction，减少每轮 token
5. **批处理（Batching）**：独立调用合并并发，降延迟也降单价
6. **预算 / 配额（Budget）**：单次任务 token 上限，超限中止

### 与你作品集的对应
- max_steps 已有（Layer 4 demo 的 token 膨胀正是成本信号）
- 资金系统场景：只读查询多、推理少 → 路由 / 分类用弱模型，仅"生成治理建议"用强模型
- 压缩已在 Layer 4 涉及

### 失败案例（无成本控制）
- ReAct 死循环（Layer 3 demo）缺 max_steps → 无限调模型烧钱
- 每轮把完整历史重发给强模型 → token 指数膨胀（Layer 4 已演示）
