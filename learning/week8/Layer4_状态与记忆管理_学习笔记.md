# Layer 4 状态与记忆管理 — 学习笔记

> 讲解结构：总（全景认知）→ 分（短期记忆 / 长期记忆 / 参考实现）→ 总（总结 + 作品集落地）

---

## 【总】全景认知：记忆管理到底在管什么

**一句话**：大模型本身是**无状态（stateless）**的——每次 API 调用都是一次孤立的请求-响应，模型不保留任何跨调用的上下文。Agent 能"记住"东西，全靠 **Harness（运行支撑层，即此前笔记所称"宿主代码 / host code"）在管理上下文**。记忆管理，就是为这个无状态的模型构建一套**上下文持久化与检索系统**——它属于 Harness 六项核心职责之一（详见 Day 1 笔记"Agent 的构成：LLM + Harness"）。

**为什么它比 RAG 检索难？**
- RAG 检索的对象是**静态文档**（文档内容固定，按需检索）
- 记忆管理的对象是**动态的、多类型的、有生命周期的**信息（会新增、会过期、会冲突、要遗忘）

**全景框架（两层 + 三件事）**：

```
记忆管理 = 为无状态模型提供上下文持久化能力
   ├─ 短期记忆（驻留于上下文窗口内，生命周期为本轮对话）
   │     管的是：窗口有限 vs 任务长 的矛盾
   └─ 长期记忆（持久化于外部存储，跨会话）
         管的是：存什么 / 怎么取 / 怎么扔
```

无论哪层，都绕不开三件事：**存什么、怎么取、怎么扔**。

---

## 【分】细节一：短期记忆（工作记忆）

**是什么**：就是你前面 demo 跑的那个 `messages` 数组 + scratchpad（显式状态字典），均位于上下文窗口内，对话结束即被丢弃。

**核心矛盾**：上下文窗口大小有限（比如几万字），但任务可能跑几十轮、查一堆工具，历史和工具结果越积越长，最后装不下。你 demo 里数组 `2→14`、token `809→5197` 就是这个矛盾的真实体现。

**四种工程做法**：

1. **滑动窗口 + 摘要压缩**（最主流，LangGraph/AutoGPT 都这么干）
   - 只保留最近 N 轮原始对话，更早的历史让模型压成一段摘要
   - 你 demo 里的 compaction（14 条压成 1 条）就是这一种的简化版

2. **分层摘要**（避免多次压缩把信息压没了）
   - 不是一次性压，而是每 5 轮生成小摘要，每 5 个小摘要再合并成大摘要
   - 类比：日志的层级 compaction

3. **关键信息锚定（Pinning）**（长任务 Agent 如 Devin 常用）
   - 任务目标、约束条件这类"绝不能丢"的信息，单独固定在 prompt 头部
   - 不参与压缩/淘汰逻辑
   - **对你作品集的启发**：你 demo 里把"熔断阈值 5%、限流 50 笔/秒"写在 system 提示——这就是锚定雏形；Layer 5 的人工闸门规则必须 pin 在头部，绝不能进压缩被丢掉

4. **Token 预算管理**
   - 给"对话历史 / 工具结果 / 系统指令"显式分配 token 配额
   - 超了就触发压缩或截断，而不是自然溢出

## 【分】细节二：长期记忆（跨会话持久化）

短期记忆在对话结束后即丢失，但"恒誉熔断阈值 5%"这类信息需要长期保留。长期记忆持久化于外部存储。

### 2.1 按内容类型分三类（参考 MemGPT/Letta）

| 类型 | 存什么 | 存哪 | 例子 |
|---|---|---|---|
| 情景记忆 | 发生过啥（时间序列） | 原始日志/对象存储 | "上周处理过恒誉一次失败率异常" |
| 语义记忆 | 抽取的事实、实体关系 | 向量库/图库 | "恒誉熔断阈值 5%" |
| 程序性记忆 | 操作习惯、成功套路 | 系统提示/代码 | "排查先查指标→历史→规则" |

### 2.2 存储层：混合存储三件套（不是单一向量库）

这是系统框架里最值钱的一点——**生产系统很少只用向量库**：
- **向量库**：存语义记忆，做相似度检索（你 RAG 作品集直接复用）
- **结构化存储（SQL/图库）**：存精确事实（如用户画像、实体关系）。向量检索处理不好"恒誉限流阈值是多少"这种精确匹配——它会给你相似的，但不保证精确
- **KV/对象存储**：存原始情景记忆（完整对话记录），按需回溯

> 为什么不能只向量库：精确查询 + 相似查询是两种需求，单一向量库顾不好精确。

### 2.3 写入策略：什么时候、写什么

最容易被低估——不是每句话都值得存：
- **反思式写入**：会话/任务结束后，让模型做一次"总结提炼"，判断哪些值得沉淀为长期记忆（MemGPT、Generative Agents 的做法），而非实时全量写入
- **重要性打分**：给每条候选记忆打分（新颖度、与目标相关性），分低的直接丢，避免记忆库变成垃圾场
- **去重与合并**：新信息进来先检索是否已有相似记忆，决定更新已有还是新建，避免同一事实反复堆积、互相矛盾

### 2.4 读取策略：什么时候查、怎么排

- **LLM 自决是否检索**：不是每次都查全部记忆，让模型自己决定"现在要不要调记忆检索工具、查哪类"
- **重排序不只看相似度**：生产常加**时间衰减因子**（越近的越优先）和**重要性权重**，综合排序取 top-k（Generative Agents 的"时近性+重要性+相关性"思路）

### 2.5 遗忘机制（很多人忽略，但生产必须有）

- **TTL 过期**：临时信息（如"今日天气"）设生存时间，到期自动删
- **容量淘汰**：库超阈值时按重要性分数做 LRU 式淘汰
- **主动遗忘（合规硬需求）**：用户要求删除（GDPR/国内个保法），企业级应用必须有删除接口

## 【分】细节三：参考实现（理解设计思路用）

- **MemGPT（现 Letta）**：将操作系统的虚拟内存管理思路移植到对话上下文——上下文窗口视为高速但容量有限的"内存"，外部存储视为"外存"，在两者间自动换入换出（swap）。这是 MemGPT 论文的核心设计思路。
- **Generative Agents（斯坦福"西部世界小镇"）**：记忆打分 = 时近性 + 重要性 + 相关性，被广泛借鉴。
- **Java 视角**：LangChain4j 的 Memory 模块、Spring AI 的 ChatMemory 接口——你 Java 背景看这两个，比纯理论有体感。

---

## 【总】总结：回到全景

记忆管理 = 为无状态模型构建记忆能力，分两层：

| 层 | 活在哪 | 核心矛盾/动作 |
|---|---|---|
| 短期记忆 | 上下文窗口 | 窗口有限 vs 任务长 → 滑动窗口/分层摘要/锚定 pinning/token 预算 |
| 长期记忆 | 外部存储 | 存什么(三类)/怎么存(混合存储)/怎么取(自决+重排序)/怎么扔(遗忘三机制) |

**对你作品集 `funding-gateway-ai-guardian` 的落地启示**：
1. 短期：沿用 demo 的 `messages` 数组 + scratchpad，且把**确定性安全规则 pin 在 prompt 头部**（永不压缩）
2. 长期（如果做）：用**混合存储**——精确查询（如"某机构限流阈值"）走 SQL，相似检索走向量库（可复用作品集一的 RAG 能力）
3. 遗忘：金融合规场景必须留**用户主动删除记忆**的接口
4. 两作品集关联点：作品集一的 RAG 检索能力，正好可作作品集二 Agent 的长期记忆检索模块

**一句话收尾**：记忆管理的本质，是替无状态的模型，把"该记的"结构化存好、"该取的"按需取回、"该扔的"按时扔掉。
