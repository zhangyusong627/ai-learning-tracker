# Agent 学习路线图与教学计划

> 创建日期：2026-08-06
> 定位：系统化、体系化的 Agent（智能体）学习路线图，含作品集规划
> 前置条件：RAG 基础已完成（Week 1-7），RAG 作品集已收尾冻结
> 教学红线：代码由 AI 写/跑，用户只做核心判断、选方案、讲理由；说人话，不甩术语

---

## 一、整体设计理念

### 1.1 为什么不直接上框架

LangGraph、LangChain Agent、AutoGen 这些框架是"脚手架"，不是"地基"。如果不懂 Agent 的循环、状态、工具、终止条件是怎么回事，框架就是黑箱——面试官问"你这个 Agent 的状态是怎么管理的"，你只能说"框架帮我管了"，这等于没做。

所以路线图的设计原则是：**先用纯代码理解原理，再用框架解决工程问题**。每一层都是"先裸写一个能跑的最小版本，再看框架在这个层面帮你解决了什么"。

### 1.2 为什么用金融场景

所有教学 demo 都用同一个业务场景：**资金系统异常分析助手**。理由：

- 你有资金域机构接入经验，对授信、放款、还款、对账流程有真实理解
- 不用额外花时间理解业务，直接聚焦 Agent 本身
- 面试时能如实串联：基于自己的资金域经验，用合成数据设计异常分析场景，同时严格隔离公司内部资料

### 1.3 与作品集的关系

学习过程和作品集是**两条线但有关联**：

- **作品集一（已完成）**：金融机构接入 RAG Skill —— 证明 RAG 工程能力，流程是固定工作流，不需要 Agent
- **作品集二（新建）**：资金系统异常分析 Agent —— 证明 Agent、工具调用、安全闸门、人在回路能力
- 两个项目独立仓库、独立业务目标、独立评测体系
- 关联点：作品集一的 RAG 检索能力将来可作为作品集二 Agent 的一个只读知识检索工具

### Layer 1：心智模型 ✅

**目标**：能判断什么任务用固定工作流，什么任务用 Agent；理解 Agent 最小循环。

**已完成内容**：
- 固定工作流 vs Agent 的判断标准：确定性/可穷举 → 工作流；不确定性/需探索 → Agent
- Agent 最小循环：目标 → 状态 → 判断 → 选工具 → 执行 → 更新 → 继续/终止
- Tool Calling 点单机制：模型只声明调用什么+传什么参数，真正执行的是代码
- 终止条件三层：正常终止（模型说够了）、兜底终止（最大步数）、异常终止（出错停）
- 失败恢复：查询类失败可重试/换工具，执行类失败必须停+人工介入

**验证标准**（已通过）：
- ✅ 能口头区分工作流和 Agent，并给选型理由
- ✅ 能解释"模型点单、代码执行"
- ✅ 能解释终止条件双层保障和失败恢复分类

### Layer 2：工具调用机制（Tool Calling）

**目标**：用真实大模型跑通一次完整的工具调用，理解工具定义、参数校验、执行控制。

**教学内容**：

1. **工具定义的三要素**：名称、描述、参数 schema（参数名、类型、是否必填、描述）
   - 类比 Java：工具定义就像写接口，参数 schema 就像 DTO 的字段注解
   - 模型通过读工具描述来决定"点哪个单"

2. **真实模型工具调用的完整链路**：
   ```
   用户提问 → 模型读到工具菜单 → 模型输出"我要调用 query_metrics，参数是机构=恒誉"
   → 代码层校验参数 → 代码执行查询 → 结果回传给模型 → 模型根据结果决定下一步
   ```
   - 关键认知：模型输出的是结构化 JSON（工具名+参数），不是自然语言
   - 代码层是安全边界：参数可以校验、执行可以拦截、结果可以过滤

3. **工具设计原则**：
   - 工具描述要写给模型看，不是写给人看——描述清楚"这个工具能干什么、什么时候该用"
   - 参数越少越好，能从上下文推断的不要让模型传
   - 只读工具和写操作工具分开管理（写操作必须人工确认，Layer 5 讲）

**工程化 demo**：
- 场景：资金系统异常分析助手
- 三个只读工具：`query_metrics`（查当前指标）、`query_history`（查历史事件）、`query_governance_rules`（查治理规则）
- 用 DeepSeek 真实模型 + Function Calling，跑通"模型选工具 → 代码执行 → 结果回传 → 模型继续判断"
- 代码由 AI 写好并运行，用户观察模型的行为并做判断题

**验证标准**：
- 能解释工具定义三要素，并指出"工具描述是写给模型看的"
- 能看着模型的真实输出，说出"模型这一步为什么选了这个工具、传了什么参数"
- 能判断"如果工具描述写得不清楚，模型会出什么问题"

### Layer 3：Agent 范式（Patterns）

**目标**：理解三种主流 Agent 范式的区别、适用场景和优缺点，能根据任务特点选范式。

**教学内容**：

1. **ReAct（边想边做）**：
   - 循环：Thought（思考）→ Action（行动/调工具）→ Observation（观察结果）→ 再 Thought
   - 适合：探索性任务，不知道一开始该干什么，需要边做边判断
   - 例子：异常分析——先查指标，看了指标发现某些字段异常，再查历史，看了历史发现是某个规则触发
   - 优点：灵活，能应对未知情况
   - 缺点：可能绕弯路，步数不可控

2. **Plan-and-Execute（先计划再执行）**：
   - 先让模型制定一个步骤清单，然后逐步执行
   - 适合：任务可以预先拆解，步骤之间有明确依赖
   - 例子：分析异常——先计划"1.查指标 2.查历史 3.查规则 4.汇总"，然后按计划执行
   - 优点：结构清晰，步数可控
   - 缺点：计划可能不准，中途发现走不通要重新规划

3. **Reflection（自我反思）**：
   - 执行完一轮后，让模型自我评估"我做得对不对、有没有遗漏"，不对就修正
   - 适合：对结果质量要求高的任务
   - 例子：分析完异常后，让模型自检"我的结论有证据支撑吗？有没有该查但没查的？"
   - 优点：提高结果质量
   - 缺点：多一轮调用，成本更高

**工程化 demo**：
- 同一个异常分析场景，用三种范式各跑一遍
- 用户对比观察：ReAct 的路径 vs Plan-and-Execute 的路径 vs 加了 Reflection 的路径
- 用户判断题：给三个不同特点的任务，选哪种范式最合适，讲理由

**验证标准**：
- 能用自己的话解释三种范式的区别
- 能根据任务特点选范式并讲理由
- 能指出 ReAct 的"绕弯路"风险和 Plan-and-Execute 的"计划不准"风险

### Layer 4：状态管理（State Management）

**目标**：理解 Agent 的状态是什么、怎么设计、怎么管，知道框架在这个层面解决了什么问题。

**教学内容**：

1. **状态是什么**：
   - Agent 的"记忆"——记录"我已经做了什么、拿到了什么信息、还差什么"
   - 本质是一个数据结构（Python 字典 / Java 对象），每轮循环更新
   - Day 1 的 bug 已经让你体验过"状态键名不一致 = Agent 失忆"

2. **状态 schema 设计**：
   - 哪些信息要存：目标、当前步骤、已获取的数据、已调用的工具历史、待确认的动作
   - 键名必须代码统一（不能让模型随意起名）
   - 类型约束：用 Pydantic / TypedDict / dataclass 强制结构（类比 Java DTO）

3. **上下文窗口管理**：
   - 模型的上下文窗口有上限（DeepSeek 约 64K token），对话太长会超限
   - 策略：只传必要信息给模型，不把整个状态原样塞进去
   - 对话历史压缩：超过 N 轮就把前面的轮次摘要成一段文字
   - 类比 Java：就像方法参数只传需要的，不是把整个对象图传进去

4. **状态持久化与恢复**：
   - checkpoint（检查点）：把状态存到文件/数据库，Agent 中断后能从断点恢复
   - 场景：Agent 跑到第 5 步等人工审批，审批通过后从第 5 步继续，不用从头来
   - 类比 Java：就像流程引擎的 suspend/resume，或者 Spring 状态机的持久化

5. **框架解决了什么**：
   - 纯代码：状态是字典，手动维护，容易出错（Day 1 的 bug）
   - LangGraph：用 StateGraph 强制状态结构，自动管理 checkpoint，框架帮你管"存什么、怎么传给模型"
   - 但框架的代价：学习成本、调试黑箱、灵活性降低

**工程化 demo**：
- 给异常分析 Agent 设计完整状态 schema
- 演示"上下文超限"问题：对话超过 10 轮后，压缩历史再继续
- 演示 checkpoint：Agent 跑到一半存盘，重新加载后从断点继续
- 代码由 AI 写，用户做"状态 schema 设计"的核心决策（哪些字段该存、哪些不该存）

**验证标准**：
- 能设计一个合理的状态 schema，并解释每个字段为什么需要
- 能解释"上下文窗口管理"为什么重要，压缩策略是什么
- 能解释 checkpoint 的价值，以及在什么场景下需要
- 能说出 LangGraph StateGraph 比纯代码字典好在哪

### Layer 5：工程化（Production Engineering）

**目标**：把一个"能跑的 demo"变成"靠谱的系统"——错误处理、人工闸门、可观测性、成本控制。

**教学内容**：

1. **错误处理与重试**（Day 1 概念已讲，这里深入工程化）：
   - 分类：工具超时 / 工具返回空 / 工具返回错误 / 模型输出异常
   - 策略：可重试错误退避重试（指数退避），不可重试错误直接停
   - 防呆：同一工具重复调用 N 次就停（Day 1 的 bug 就是这个问题的简化版）
   - 关联已学：code_synth_agent 的 E6001 可重试 / E2003 不重试，同一思维

2. **人工参与闭环（Human-in-the-loop）**：
   - 哪些动作必须人工确认：写操作（改配置、改限流、发告警）、高风险动作、模型不确定的动作
   - 状态机：`pending_approval`（待审批）→ `approved`（批准）/ `rejected`（拒绝）
   - 审批后继续：从 checkpoint 恢复，执行被批准的动作
   - 关联已学：RAG 作品集的 candidate → approved 人工审核，同一模式
   - 类比 Java：就像工作流引擎的审批节点

3. **可观测性（Observability）**：
   - 日志：每一步记录"调了什么工具、传了什么参数、返回了什么、模型判断了什么"
   - 追踪：能回溯 Agent 的完整执行路径（从第一步到最后一步）
   - 指标：工具调用成功率、平均步数、token 消耗
   - 类比 Java：就像 ELK + SkyWalking，Agent 也需要"调用链追踪"

4. **成本控制**：
   - token 是花钱的：每轮循环都调模型，步数越多越贵
   - 步数上限：max_steps 不只是防死循环，也是控成本
   - 模型选择：简单判断用小模型，复杂推理用大模型
   - 缓存：相同输入不重复调模型

5. **安全防护**：
   - 越权拦截：Agent 不能执行超出其权限的动作（只读 Agent 不能写）
   - 危险动作阻止：删数据、改配置、发通知——必须人工确认
   - 输入注入防护：用户输入里藏的恶意指令不能让 Agent 执行危险操作

**工程化 demo**：
- 给异常分析 Agent 加完整工程化：
  - 工具失败自动重试 + 重复调用检测
  - "建议调整限流阈值"走人工审批流程
  - 每步执行日志 + 完整执行路径回溯
  - token 消耗统计
  - 越权动作拦截演示
- 代码由 AI 写，用户做"哪些动作需要人工确认"的决策

**验证标准**：
- 能分类工具失败场景并给出处理策略
- 能设计人工审批闸门的状态机
- 能解释可观测性为什么对 Agent 特别重要
- 能说出至少 3 种成本控制手段
- 能识别越权动作并设计拦截方案

### Layer 6：多智能体（Multi-Agent）

**目标**：理解什么时候需要多个 Agent、怎么协作、什么时候不需要。

**教学内容**：

1. **什么时候需要多 Agent**：
   - 单个 Agent 能搞定的，不要拆——多 Agent 不是越多越好
   - 需要拆的场景：任务跨度大（一个查数据、一个分析、一个写报告）、专业领域不同（一个懂数据库、一个懂业务规则）、需要并行处理
   - 反面教材：为了"多智能体"而拆，实际增加了协调成本和出错概率

2. **协作模式**：
   - **串行**：Agent A 做完交给 Agent B（A 查数据 → B 分析 → C 写报告）
   - **并行**：Agent A 和 B 同时做不同的事，结果汇总
   - **监督者-执行者**：一个 Supervisor Agent 分配任务给多个 Worker Agent
   - 类比 Java：就像微服务编排——串行调用、并行调用、或者有个编排器

3. **Agent 间通信**：
   - 共享状态：多个 Agent 读写同一个状态对象
   - 消息传递：Agent A 的输出作为 Agent B 的输入
   - 关键问题：怎么保证信息不丢、不冲突

**工程化 demo**：
- 异常分析场景拆成两个 Agent：
  - Agent A（数据收集）：负责查指标、查历史、查规则，输出"原始数据包"
  - Agent B（分析建议）：接收数据包，分析异常原因，输出"建议+证据+风险"
- 演示串行协作的完整链路
- 对比单 Agent 做全部事情的方案，讨论拆分的利弊
- 用户判断题：这个场景拆成两个 Agent 值不值？什么情况下才值得拆？

**验证标准**：
- 能判断什么场景需要多 Agent，什么场景不需要
- 能解释三种协作模式的区别
- 能说出多 Agent 的协调成本和风险

### Layer 7：评估与安全（Evaluation & Safety）

**目标**：能设计 Agent 的测试场景、定义评估指标、做安全防护。

**教学内容**：

1. **测试场景设计**（至少 6 种）：
   - 正常完成：Agent 按预期走完流程，给出正确建议
   - 工具调用失败：某个工具超时或返回错误，Agent 能正确处理
   - 无证据：查不到相关信息，Agent 能说"信息不足"而不是编答案
   - 越权动作：Agent 试图执行超出权限的操作，被拦截
   - 人工拒绝：建议被人工拒绝，Agent 能接受并终止
   - 达到最大步数：Agent 没能在步数上限内完成，被强制终止

2. **评估指标**（中文解释）：
   - 工具调用成功率：调了 N 次工具，成功几次
   - 任务完成率：给 M 个任务，正确完成几个
   - 平均执行步数：完成一个任务平均需要几轮循环
   - 危险动作拦截率：有多少次危险动作被成功拦截
   - 人工改判率：人工审批中有多少比例被拒绝或修改
   - 拒答准确率：无答案问题中，正确拒答的比例

3. **安全防护**：
   - 提示注入（Prompt Injection）：用户输入里藏指令，试图让 Agent 执行非预期操作
   - 工具滥用：Agent 被诱导频繁调用某个工具，浪费资源
   - 信息泄露：Agent 在输出中泄露不该泄露的信息（系统提示词、其他用户数据）
   - 防护手段：输入过滤、输出审查、工具调用频率限制、权限分级

4. **审计日志**：
   - 每次执行留全量日志：输入、每步决策、工具调用、输出
   - 可回溯：事后能复盘"Agent 为什么做了这个决策"
   - 关联已学：RAG 作品集的检索审计表，同一思维

**工程化 demo**：
- 给异常分析 Agent 设计完整评估方案：
  - 6 种测试场景各写一组测试用例
  - 跑完测试后输出指标报告
  - 演示一次提示注入攻击和防护
  - 审计日志回溯演示
- 代码由 AI 写，用户做"评估指标怎么定义"的决策

**验证标准**：
- 能设计至少 6 种测试场景并解释每种要验证什么
- 能定义评估指标并解释计算口径
- 能识别提示注入风险并设计防护
- 能解释审计日志对 Agent 的价值

## 三、作品集规划

### 3.1 核心决策：新建独立作品集二，不在现有 RAG Skill 上加 Agent

**新建独立仓库** `funding-gateway-ai-guardian`（资金网关 AI 智能守护），现有 `financial-institution-integration-skill` 保持不动。理由：

1. **现有 Skill 的流程是固定的**——解析、切块、检索、证据过滤、人工审批，每一步顺序和条件都写死了。这是**确定性工作流**，应该用工作流，不该用 Agent。硬加 Agent 只会增加不确定性，没有真实价值。

2. **异常分析天然适合 Agent**——系统出了问题，Agent 不知道一开始该查什么：可能是指标异常，可能是历史事件触发，可能是规则变更。需要**临场判断**先查什么、再查什么、要不要换工具、信息够了没有。这才是 Agent 的用武之地。

3. **两个作品集各有侧重，面试叙事更强**：
   - 作品集一（RAG 代码生成 Skill）：证明 RAG 工程能力——"流程确定，用固定工作流"
   - 作品集二（AI 智能守护 Agent）：证明 Agent 能力——"需要临场判断，用 Agent"
   - 面试时能讲："第一个项目我用固定工作流，第二个项目我用 Agent，因为两个场景的特点不同"——这直接展示你**理解选型**

4. **两个项目有关联但独立**：作品集一的 RAG 检索能力将来可作为作品集二 Agent 的一个只读知识检索工具（比如 Agent 觉得需要查某机构的历史接入文档，就调作品集一的检索），但两者保持独立仓库、独立业务目标和独立评测体系。

### 3.2 作品集二：资金网关 AI 智能守护

**业务场景**：资金系统异常分析与治理建议

**核心链路**：

```
合成运行指标（模拟资金系统的授信成功率、放款延迟、对账差异等异常）
  → Agent 选择只读工具查询指标、历史事件和治理规则
  → 生成调整建议与证据
  → 确定性安全规则校验（防止危险建议）
  → 人工审批（高风险动作必须人确认）
  → 模拟执行、审计与回滚（执行后留全量日志，可回滚）
```

**为什么这个场景好**：
- 你有资金域机构接入经验，对资金系统的授信、放款、还款、对账流程有真实理解
- 异常分析需要临场判断（先查什么、再查什么），天然适合 Agent
- 治理建议涉及写操作（改限流、调配置），必须人工审批，能展示安全闸门
- 合成数据不碰真实公司资料，守红线

**只读工具设计**（Agent 可自主调用）：
- `query_metrics`：查当前运行指标（授信成功率、放款延迟、失败率等）
- `query_history`：查历史异常事件（过去发生过什么类似问题）
- `query_governance_rules`：查治理规则（当前限流阈值、熔断规则等）

**写操作工具**（必须人工审批）：
- `suggest_adjustment`：建议调整某项配置（如限流阈值、熔断阈值）
- `generate_report`：生成异常分析报告

### 3.3 建设节奏

| 学习阶段 | 作品集动作 |
|---|---|
| Layer 1-3（心智模型、工具调用、范式） | 纯学习 demo，放 `learning/week8/agent-demos/`，不建仓库 |
| Layer 4（状态管理） | 开始设计异常分析 Agent 的状态 schema |
| Layer 5（工程化） | **创建独立仓库** `funding-gateway-ai-guardian`，把学习 demo 升级为正式作品集 |
| Layer 6（多智能体） | 评估作品集是否需要拆多 Agent（大概率不需要，单 Agent 够用） |
| Layer 7（评估安全） | 给作品集 Agent 加评估方案、审计日志、安全防护 |

**不在学习初期就建空仓库**，而是学到 Layer 5（工程化）、确认 demo 质量够好后，再迁移到独立仓库作为正式作品集。这样避免"先建仓库再填内容"的压力。

### 3.4 面试叙事

学完后，你的面试叙事是这样的：

> "我做了两个项目。第一个是金融机构接入的 RAG 工具——把资方 API 文档和产品需求文档解析、切块、向量化、检索，大模型只读检索证据不读原始文档，防幻觉；流程是固定的，所以用确定性工作流，不需要 Agent。
>
> 第二个是资金系统异常分析 Agent——模拟资金系统出现授信失败率升高、放款延迟等异常，Agent 自主决定查什么指标、查什么历史、查什么规则，然后生成治理建议；高风险动作（改配置、调限流）走人工审批，不是全自动执行。我还设计了评估方案，测了正常路径、工具失败、越权拦截等 6 种场景。
>
> 两个项目有关联——Agent 的一个工具可以调 RAG 检索，查机构的历史接入文档。但两个项目场景特点不同，所以选型不同：固定流程用工作流，需要临场判断用 Agent。"

## 四、教学方式

### 4.1 每一层的标准教学流程

1. **先讲概念**（大白话 + Java 类比）：这一层解决什么问题、核心概念是什么
2. **跑 demo**（AI 写好代码、运行、展示结果）：用金融场景演示这一层的核心能力
3. **用户做判断题**（不写代码）：基于 demo 的结果做核心决策
4. **失败案例**（AI 故意制造问题）：看 Agent 出了什么问题、为什么、怎么修
5. **对比框架**（这一层可选）：纯代码 vs 框架，框架帮你解决了什么、代价是什么
6. **验证**：用户能用自己的话解释这一层的核心概念

### 4.2 每层产出的学习证据

按 `LEARNING_WORKFLOW.md` 要求，每层至少留下：
- 学习目标、边界和通过标准
- 用户自己的费曼解释（核心概念掌握证据）
- 一个最小可运行实践（AI 写代码 + 运行结果）
- 一个失败案例和根因
- 概念/代码诊断/场景迁移三层测试
- 一个用户独立完成的核心决策
- 尚未掌握的内容
- 复习计划（Day +1、Day +7、Day +30）
- 面试口述记录

### 4.3 教学红线

- **代码由 AI 写/跑**，用户不写代码，只做核心判断
- **说人话**，不甩术语，英文术语首次出现必须给中文
- **一次只讲一个概念**，一次只问一个问题
- **必须先教再测**，不能用没讲过的知识测试
- **用 Java 类比**，但说明类比的失效边界

## 五、Layer 间依赖关系

```
Layer 1（心智模型）✅ → Layer 2（工具调用）✅ → Layer 3（范式）✅
                                              ↓
                                        Layer 4（状态管理）✅
                                              ↓
                                        Layer 5（工程化）✅ → 作品集沉淀✅
                                              ↓
                                        Layer 6（多智能体）✅
                                              ↓
                                        Layer 7（评估安全）✅ → 作品集收尾✅
```

- Layer 1 是所有后续的前置（已完成）
- Layer 2 是 Layer 3 的前置（要先懂工具调用，才能理解范式怎么用工具）
- Layer 3 和 Layer 4 可以交叉学（范式需要状态，状态为范式服务）
- Layer 5 依赖 Layer 2-4（工程化是给前面几层加护栏）
- Layer 6 依赖 Layer 2-5（多 Agent 是单 Agent 的扩展）
- Layer 7 依赖 Layer 2-6（评估是给整个系统做测试）
