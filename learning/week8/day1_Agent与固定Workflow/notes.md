## 2. 用户费曼解释（核心概念掌握证据）

### 固定工作流 vs Agent
- **固定工作流**：步骤、条件、判断全部由代码写死，同输入永远同一条路，确定性、可预测、可审计。适合流程明确、情况可穷举的任务（跑批、报表、定时告警）
- **Agent（智能体）**：人定目标和边界，模型临场决策每一步做什么，循环执行"看状态→判断→选工具→执行→更新→继续/终止"。适合不确定、需要探索的任务（异常诊断）
- **用户原话（选型理由）**："每天凌晨固定执行：读报表→算错误率→超阈值告警。每一步流程、条件、判断都是固定的，所以用固定工作流即可，不需要用 Agent，因为 Agent 比较适合不确定性、需要探索的任务" —— ✅ 判断正确
- **用户判断标准**：确定性/可穷举 → 工作流；不确定性/需探索 → Agent

### Tool Calling（工具调用）
- 模型不执行工具，模型只"点单"（声明调用哪个工具、传什么参数），真正执行的是我们的代码
- **用户原话**："模型是不会调用工具的，模型只会告诉你调用哪个工具，传什么参数。因为模型它是不会执行的，它只会告诉你怎么去执行" —— ✅ 理解正确
- 引申：安全边界在代码执行层（可校验、可拦截）

### Agent 的构成：LLM + Harness（运行支撑层）

业界对 Agent 的共识拆解：Agent = LLM（推理引擎）+ Harness（运行支撑层 / 编排层）。

- **LLM**：负责理解、推理、决策——决定调哪个工具、说什么话。它本身是无状态的文本生成器，不会执行任何动作。
- **Harness**：开发者围绕 LLM 编写的控制代码，负责把"会聊天的模型"变成"能办事的 Agent"。它承担六项职责：
  1. 上下文装配：把 system prompt + 历史 messages + 工具定义组装成一次 API 请求
  2. agent loop（智能体循环 / 调用循环）：发请求 → 收响应 → 解析 → 执行 → 回填 → 再发，直到终止
  3. 工具执行：按 LLM 声明的 tool_calls 实际调用函数，含安全校验与拦截
  4. 状态与记忆管理：维护 messages 数组与外部记忆存储的读写
  5. 终止与兜底：正常终止 / max_steps 强制截断 / 异常终止
  6. 错误处理与人工闸门：重试、换工具、高风险动作人工确认
- 命名变体：不同资料也称 runtime / agent loop / orchestration layer / scaffolding。核心共识一致——Agent 不是单纯一个模型，而是"模型 + 让它真正行动的支撑代码"。
- 与已学内容的对应：Layer 2 工具调用里的"宿主代码执行工具" = Harness 职责 3；Layer 4 状态管理里的"宿主代码管理上下文" = Harness 职责 4。此前笔记中的"宿主代码（host code）"即 Harness 的俗称，现统一为标准术语 Harness。

### Agent 最小循环（完整链路）
```
目标 → 当前状态 → 模型判断下一步 → 点单（选工具+参数）
→ 代码执行 → 结果回传 → 更新状态 → 继续/终止
```

## 4. 失败案例与根因（今天最有价值的收获）

**现象**：Agent 重复调用 query_history 三次，直到 max_steps=5 被强制截断。最终状态里数据其实第一轮就有了。

**根因**：状态键名不一致——`execute` 写入的键是 `近2小时`，`mock_model` 判断的键是 `历史`。模型"以为"自己没查到历史（因为找不到"历史"这个键），所以无限重复点单。数据在，标签对不上 = Agent 失忆。

**工程启示**：
1. Agent 的"记忆"= 状态里的键值对；键名必须代码统一，不能让模型随意起名
2. 终止条件双层保障：模型正常终止（返回 None）+ max_steps 兜底（防无限循环）
3. 真实系统还要加防呆：重复调用同一工具 N 次就停、工具超时、异常路径

## 追加（16:18，第 2 层前两块：终止条件 + 失败恢复）

### 终止条件（Agent 的"刹车"）——三种
- 正常终止：模型说"够了"（决策输出 None）
- 兜底终止：最大步数强制截断（防死循环烧钱）
- 异常终止：出错停止
- 认知：不能只靠模型自觉，必须配兜底——AI 负责判断，代码负责兜底（同作品集"人工闸门+确定性校验"思维）
- 配套代码：day1_termination_demo.py（死脑筋模型 vs 正常模型两种刹车演示）

### 失败恢复（用户独立判断 ✅）
- 用户答案：工具失败换工具再试（B），且重试次数不超过兜底上限 —— ✅ 判断正确 + 自己补了封顶约束（工程直觉）
- 补充：不搞一刀切，按失败性质分类：
  - 查询类失败（拿不到信息）→ 可重试/换工具，信息缺失不致命
  - 执行类失败（动作没做成）→ 必须停 + 人工介入，不能自作主张
- 关联已学：code_synth_agent 重试策略同理——可重试错误（E6001）退避重试，业务拒绝（E2003）不重试直接抛。Agent 失败恢复 = 同一思维从错误码升级到工具调用
