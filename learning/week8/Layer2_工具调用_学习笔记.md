# Layer 2 工具调用机制 — 学习笔记

> 日期：2026-08-06
> 定位：用真实大模型跑通工具调用链路，理解"模型点单、代码执行"
> 关联：Agent学习路线图与教学计划.md → Layer 2

---

## 一、学习目标

- 理解工具定义三要素（名称、描述、参数结构）
- 用真实模型跑通"模型点单 → 代码执行 → 结果回传 → 模型继续"的完整链路
- 理解为什么"工具描述是写给模型看的"

## 二、核心概念（费曼式）

1. **模型是函数调用（function calling）的发起方，宿主代码（host code）是执行方**：模型只输出结构化的 tool_calls（JSON，含工具名+参数），由宿主代码负责解析并执行实际工具（查库、调接口等）。模型本身不具备执行外部操作的能力。
2. **工具定义三要素**：
   - 名称（如 `query_metrics`）
   - 描述（**写给模型看**，讲清楚"我是干什么的、什么时候该用我"）
   - 参数结构（参数名、类型、是否必填、描述——类似 Java DTO 字段注解）
3. **完整链路**：用户提问 → 模型读工具菜单 → 输出 tool_calls(JSON) → 代码校验+执行 → 结果回传 → 模型决定下一步（再调工具 or 给最终答案）。
4. **代码层是安全边界**：参数可校验、执行可拦截、结果可过滤。

## 三、真实 Demo 结果（layer2_tool_calling_demo.py）

场景：恒誉消金授信失败率变高。模型第 1 轮**并行**点了 3 个工具：
- `query_metrics(恒誉消金)` → 失败率 8.8%
- `query_history(恒誉消金)` → 2026-03-12 类似事件（征信接口超时）
- `query_governance_rules()` → 熔断阈值 ≥5%

第 2 轮模型综合三份数据给出分析：8.8% 已超 5% 熔断阈值，参考历史建议排查上游征信接口。

**关键观察**：
- 模型输出的是 JSON，不是自然语言
- 模型自主推导该查哪三个、什么顺序（并行因为互相独立）
- 模型严格基于工具返回数据，没编数据

## 四、踩坑记录（demo 代码 bug，非概念错误）

第一轮报错 HTTP 400：`assistant message with tool_calls must be followed by tool messages`。

根因：把"含 tool_calls 的助手消息"在循环里对每个工具都 append 了一次，导致消息顺序违反 API 强约束。修正：助手消息只追加一次，工具消息在循环内追加。

**启示**：工具调用代码的消息顺序有严格契约——助手(tool_calls) 必须紧跟对应的 tool 消息，且每个 tool_call_id 都要有回应。

## 五、失败案例实验（layer2_bad_description_experiment.py）

变量：只把 `query_history` 描述从"查询指定机构历史上发生过的类似异常事件及当时处理方式"改成"查询历史"。

结果：**模型行为本轮未变**（照样点 query_history，参数恒誉消金）。

根因分析：模型同时读三个信号——① 系统提示词（点名"历史"）② 参数描述（institution 仍写"机构简称"）③ 工具描述。前两个兜底了。

**真实风险**：当 Agent 有十几个名字相似的工具（query_history/query_event_log/query_audit_trail），系统提示词无法逐个枚举，工具描述成为模型区分的唯一依据——那时候写烂就真乱点了。

**工程铁律**：工具描述宁可啰嗦，不能模糊。

## 六、用户费曼（核心掌握证据）

用户原话："他可能会去查其他机构，或者所有机构的历史的异常事件。"

评估：方向正确（描述含糊→模型不知边界），但需修正——因 institution 必填，不会字面查所有机构；真实风险在工具多/相似时。
